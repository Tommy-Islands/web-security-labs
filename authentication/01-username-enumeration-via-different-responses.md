# Authentication：ログイン失敗時のレスポンス差によるユーザー名列挙

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Username enumeration via different responses |
| 難易度 | Apprentice |

| 検証日 | 2026年11月6日 |
| 対象 | ログイン機能（`POST /login`） |
| ツール | Burp Suite Community Edition（Intruder） |
| 結果 | LAB Solved |
| 理解度チェック | 5/5問正解（100%） |

### 検証目的

存在するユーザー名と存在しないユーザー名で認証失敗時のレスポンスが変わる場合に、攻撃者がユーザー名を列挙できるか検証する。さらに、特定したユーザー名に対してパスワード候補を試すことで、認証成功に到達できるか確認する。

**検証対象はPortSwiggerの許可された学習用ラボのみ。**

---

## 2. 実務上の攻撃シナリオ

### 2.1 想定するシステムと攻撃者

一般公開されたWebサービスのログイン画面を想定する。外部利用者が任意のユーザー名とパスワードを入力できる。攻撃者は有効なアカウント名を知らないが、ログイン失敗時の応答を比較できる。

### 2.2 攻撃から被害までの流れ

1. 攻撃者が複数のユーザー名候補を送信する。
2. 存在しないユーザー名は `Invalid username`、実在するユーザー名と誤ったパスワードの組み合わせでは `Incorrect password` となり、差が生じる。
3. 応答本文または長さの差から、実在するユーザー名を特定する。
4. 特定したアカウントに対してパスワード候補を試行し、応答ステータスの変化からログイン成功を探す。
5. 弱いパスワードが使われ、試行回数制御などが不十分なら、第三者によるアカウントへの不正ログインにつながるおそれがある。

### 2.3 想定被害・根本原因・対策の対応

| 観点 | 内容 |
|---|---|
| 想定被害 | アカウントの乗っ取り、個人情報の閲覧、登録情報の改変、不正な操作 |
| ユーザー名列挙の根本原因 | ユーザー名の存在有無によりログイン失敗時のメッセージ・レスポンスが異なる |
| 侵入を助けた追加条件 | 弱いパスワードと、繰り返し試行を十分に制限できない認証処理 |
| 直接的な防止策 | ユーザー名の存在有無によらず認証失敗応答を統一する。長さ・ステータス・時間差にも注意する |
| 追加の防止策 | パスワード試行のレート制限、アカウント保護、MFA、漏えいパスワードの利用防止 |
| 検知策 | 多数の異なるユーザー名やパスワードを用いた連続ログイン試行、試行元IP・対象アカウント・成功/失敗のログを監視する |

**ここで挙げた被害は実務上の想定であり、実在企業でのインシデントを実証したものではない。**

## 3. 技術的背景

### 3.1 ユーザー名列挙（Username Enumeration）

ログイン画面がユーザー名の存在有無について異なる応答を返すと、攻撃者は有効なアカウント名を推測できる。

今回のラボでは次のメッセージ差が確認された。

- 存在しないユーザー名：`Invalid username`
- 実在するユーザー名と不正なパスワード：`Incorrect password`

`Length` の差は候補を絞り込む手掛かりであり、メッセージ本文の違いを確認したことが重要な証拠となる。

### 3.2 Burp Intruderの攻撃位置

Intruderでは ``username=`candidate`&password=test`` のように、```` で囲んだ箇所をペイロードの差し替え位置として指定できる。

今回は最初に `username`、次に `password` を候補リストで変更して試行した。

### 3.3 ステータス302について

HTTP `302 Found` はリダイレクトを示す。今回のラボではパスワード候補の結果一覧で302を返した行がログイン成功と対応し、実際にその資格情報でログインしてSolvedを確認した。

**302という数字だけで、どのアプリケーションでも認証成功と判定できるわけではない。** 実際の遷移先と認証状態も確認する必要がある。

## 4. 検証手順

### STEP 1：ログインリクエストを記録

ログイン画面で適当なユーザー名・パスワードを入力し、`POST /login` をBurp Suiteで記録した。

### STEP 2：ユーザー名候補を試行

`POST /login` をIntruderへ送り、`username` を攻撃位置に指定。PortSwigger公式のユーザー名候補リストを使用した。

結果一覧を `Length` 列でソートし、大半と長さの違う1行を発見した。

### STEP 3：エラーメッセージの違いを確認

多くの候補では `Invalid username` と表示された一方、1件だけ `Incorrect password` と表示された。

この候補から**存在するユーザー名 `acid` を特定**した。

### STEP 4：パスワード候補を試行

`username=acid` に固定し、Intruderの攻撃位置を `password` に変更。PortSwigger公式のパスワード候補リストを試行した。

### STEP 5：ログイン成功を判定

`Status` 列をソートして `302` の行を見つけ、対応するパスワード `12345678` を特定した。

### STEP 6：再現確認

`acid` / `12345678` でログインし、**ラボのSolved表示を確認**した。

## 5. 実証HTTP（再現用の例示）

**重要：以下はユーザーから共有された検証内容を基に構成した説明用HTTP例である。実際のBurp通信全文を保存した証拠ではない。** ドメインとCookieは非掲載。

### 5.1 ユーザー名候補のリクエスト例

```http
POST /login HTTP/1.1
Host: <lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

username=not-a-valid-user&password=test
```

**検証で報告された応答本文の特徴：**

```text
Invalid username
```

### 5.2 実在ユーザー名のリクエスト例

```http
POST /login HTTP/1.1
Host: <lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

username=acid&password=test
```

**検証で報告された応答本文の特徴：**

```text
Incorrect password
```

上記2例のHTTPステータス、Content-Length、完全なHTML本文は未提供のため記載していない。`Length` 列に差が生じたことは観測結果として記録する。

### 5.3 認証成功のリクエスト・レスポンス例

```http
POST /login HTTP/1.1
Host: <lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

username=acid&password=12345678
```

**確認したステータス（ヘッダー全体は未提供）：**

```http
HTTP/1.1 302 Found
```

実際のHTTPバージョン、`Location`、`Set-Cookie` 等は未確認。この例のHTTP/1.1は説明用であり、実際の通信で確認されたHTTPバージョンを表さない。

## 6. 検証結果と根本原因

| フェーズ | 検証した入力・操作 | 実際に確認された結果 |
|---|---|---|
| ユーザー名列挙 | `username` の公式候補リスト | `Length` が異なる1行を発見 |
| メッセージ比較 | 複数のユーザー名候補 | `Invalid username` と `Incorrect password` の違い |
| ユーザー名特定 | 異なる応答の候補 | `acid` を特定 |
| パスワード探索 | `username=acid` で公式候補リスト | `Status=302` の行から `12345678` を特定 |
| ログイン再現 | `acid` / `12345678` | ログインし、LAB Solved |

根本原因は、認証失敗時に**ユーザーの存在有無という本来秘匿すべき情報を、応答の違いとして外部へ漏らしていること**。

パスワードの推測が成立した点には、別の問題としてパスワードの強度や試行回数制御も関わる。**ユーザー名列挙とパスワード総当たりは関連するが、同じ脆弱性ではない**。

## 7. 推奨対策と検知

### 7.1 認証失敗の応答を統一する

存在しないユーザー名と誤ったパスワードで、どちらも「ユーザー名またはパスワードが正しくありません」などの共通メッセージを返す。

本文の違いだけでなく、HTTPステータス・応答長・処理時間などが列挙の手掛かりにならないように確認する。完全に一律の処理時間を保証するという意味ではない。

### 7.2 パスワード試行を制限する

アカウント単位・試行元単位・全体のレート制限、段階的な追加認証、適切な監視を組み合わせる。ロックアウトを設ける場合は第三者によるサービス妨害を考慮する。

### 7.3 認証を強化する

MFA、漏えい済みパスワードの拒否、十分な長さのパスワードの推奨などを実装する。エラーメッセージ統一だけでは弱いパスワードの問題は解消しない。

### 7.4 ログ監視

ログイン失敗数の急増、1つのIPから多数のユーザー名への試行、1ユーザー名への多数のパスワード候補試行、失敗直後のログイン成功を検知し、調査につなげる。

---

## 8. 実務上の想定影響

ユーザー名の列挙により標的アカウントが判明し、パスワード推測やクレデンシャルスタッフィングの効率が上がる可能性がある。

さらに認証が突破されると、ユーザーの権限で閲覧・変更できる個人情報や操作に被害が及ぶおそれがある。

**今回は学習ラボの `acid` でSolvedを確認したのみで、実在する第三者のアカウントへのアクセスはしていない。**

---

## 9. 未検証事項・制約

- 実際の `POST /login` の完全なHTTPリクエスト・レスポンスとヘッダー
- ユーザー名候補ごとの正確な `Length` 数値・ステータス
- 認証成功時の `Location` ヘッダー・セッションCookie・実際のHTTPバージョン
- アプリケーション内部のユーザー検索・認証判定処理
- レート制限・アカウントロック・MFA等の有無
- 他の候補・他のログイン画面での再現性
- 実在システムでの被害

報告された操作と観測結果を実証、構成したHTTP例は例示、一般的な影響は想定として区別する。
