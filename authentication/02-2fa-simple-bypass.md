# Authentication：2FAの完了前に保護ページへアクセスできる認証フローの不備

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | 2FA simple bypass |
| 難易度 | Apprentice |
| カテゴリ | Authentication / Multi-factor |
| 検証日 | 2026年11月6日 |
| 使用環境 | ブラウザ、学習ラボ付属のEmail client |
| Burp Suite | 使用せず |
| 対象ページ | ログイン画面、2FAコード入力画面、`/my-account` |

| 理解度チェック | 5/5問正解（100%） |

### 検証目的

ユーザー名・パスワードによる一次認証後、2FA（第二要素の確認）を完了する前に、保護されたアカウントページへ直接アクセスできるか検証する。ログイン処理の各段階でサーバーが認証状態を適切に管理しているかを理解する。

※ 本検証は許可された学習用環境のみで実施した。

---

## 2. 実務上の攻撃シナリオ

### 2.1 想定するシステム

会員制サービスが、パスワード認証の後にメール等で確認コードを送る二要素認証を導入している。正式なログインの完了には、一次認証と2FAの両方が必要となる。

会員情報を表示する `/my-account` は、本来、認証を最後まで完了したユーザーだけに公開される保護ページである。

### 2.2 攻撃者の立場

攻撃者は何らかの理由で他人の有効なユーザー名・パスワードを知っているが、2FAコードは入手していないと想定する。

重要なのは、**今回のラボは一次認証の突破を検証したものではない**という点。攻撃者は一次認証を通過できるという前提で、第二要素のチェックを回避できるか試している。

### 2.3 攻撃から被害までの流れ

1. 利用者は正しいユーザー名とパスワードを送信する。
2. アプリケーションは2FAコード入力画面を表示する。通常は正しいコードの入力後に保護ページへ進める。
3. 攻撃者は2FAコードを入力せず、ブラウザのアドレスバーから直接 `/my-account` を指定する。
4. 保護ページ側が2FA完了済みか確認しない場合、一次認証のみの状態でもアカウントページを表示してしまう。
5. 実務では、個人情報の閲覧、アカウント設定変更、取引・購入操作などの不正実行につながるおそれがある。

### 2.4 想定被害・原因・防止策・検知策の対応

| 観点 | 内容 |
|---|---|
| 想定被害 | 2FAによる保護の無効化、アカウントへの不正アクセス、個人情報の閲覧・改変 |
| 根本原因 | 一次認証成功後のセッションを、保護ページ側で2FA完了済みのセッションと適切に区別・検証していない |
| 直接的な防止策 | サーバー側で認証の段階を管理し、2FA完了までは保護ページへのアクセスを許可しない |
| 追加の防止策 | 認証完了時のセッション更新、認証状態の遷移制御、全保護APIでの共通検証、重要操作の追加認証 |
| 検知策 | 2FA未完了のセッションによる保護URLへのアクセス、認証途中の異常なページ遷移、2FA失敗やアクセス拒否を監視 |

**想定被害は業務システムで同様の問題が存在した場合の仮説であり、実在する企業での被害を実証したものではない。**

## 3. 技術的背景

### 3.1 一次認証と二要素認証

一次認証はユーザー名・パスワードの確認。2FAはそれに加えて別の要素（例：メールの確認コード）を検証する段階。

一次認証が成功しても、2FAが未完了なら**ログインは完了していない**。

### 3.2 セッションと認証状態

サーバーは、各リクエストがどの利用者の認証処理に対応するかをセッションなどで管理する。実務上は認証の進行状態を明確に区別する必要がある。

概念的な状態遷移：

```text
未認証
  ↓ ユーザー名・パスワードの検証成功
一次認証済み / 2FA未完了
  ↓ 有効な2FAコードを検証
認証完了
  ↓
/my-account などの保護ページを許可
```

この図は一般的な安全設計の説明であり、今回のラボの内部実装を直接確認したものではない。

### 3.3 URLの直接遷移は脆弱性の原因ではない

ブラウザのアドレスバーへ `/my-account` を入力する行為自体は通常のブラウザ操作。問題は、**サーバーがそのアクセスを受け付ける際に2FA完了状態を検証していないこと**にある。

画面の表示順序やクライアント側の画面遷移だけに依存した制御は、URL直接指定で回避される可能性がある。

## 4. 検証手順と結果

### STEP 1：自分のアカウントで通常のログイン手順を確認

学習ラボに用意された自分のアカウント（`wiener`）でユーザー名・パスワードを入力してログインした。

一次認証後、4桁のセキュリティコードを求められた。

### STEP 2：2FAを正常に完了する

ラボ付属の `Email client` からセキュリティコードを確認し、コード入力画面で正しいコードを入力した。

その後、アカウントページ `/my-account` に移動できることを確認し、URLを記録した。

**確認できた事実：** 正常フローでは2FAコード入力後にアカウントページを閲覧できた。

### STEP 3：ログアウトし、別アカウントの一次認証を実施

ログアウト後、学習ラボに用意された検証対象のアカウント（`carlos`）でユーザー名・パスワードを入力した。

一次認証後、2FAのセキュリティコード入力画面が表示された。

**この時点では2FAコードは入力していない。**

### STEP 4：2FA未完了のまま保護ページへ直接遷移

セキュリティコード入力画面から、ブラウザのアドレスバーに次のパスを指定した。

```text
/my-account
```

この操作は、2FAコードの送信や検証を経由しないページ遷移。

### STEP 5：画面の変化とSolvedを確認

`/my-account` への直接遷移により、`carlos` のアカウントページが表示された。

**2FAコードを一度も入力しないまま、LAB Solvedを確認した。**

## 5. 実証した操作・画面遷移

今回は**ブラウザのみを使用したため、生のHTTPリクエスト・レスポンスは採取していない**。以下は観測した画面操作と表示結果の記録であり、HTTP通信の再現やステータスコードの推測ではない。

| 段階 | 操作・状態 | 確認された結果 |
|---|---|---|
| 正常フロー | `wiener` で一次認証 | 4桁の2FAコード入力画面を表示 |
| 正常フロー | Email clientで確認したコードを入力 | `/my-account` を閲覧できた |
| 検証フロー | `carlos` で一次認証 | 2FAコード入力画面を表示 |
| 検証フロー | コード未入力のまま `/my-account` を直接指定 | `carlos` のアカウントページを表示 |
| 最終結果 | 同じ検証フロー | LAB Solved |

### HTTPの取り扱い

実際の `GET /my-account` のHTTPバージョン、ステータスコード、Cookie、リダイレクト、レスポンス本文は観測していないため記載しない。

画面が表示されたという事実から、ブラウザの遷移とサーバーの応答が成立したと考えられるが、**どのHTTPステータスやセッションフラグが使われたかは未確認**。

## 6. 根本原因と影響の分析

### 6.1 根本原因：認証状態の管理不備

2FA未完了の状態でも、保護対象である `/my-account` へのアクセスを許可してしまう点が問題。

サーバー側は一次認証と2FAの両方が完了したことを確認しない限り、保護ページの取得や関連APIの実行を許可してはならない。

### 6.2 複数段階の認証フローで起こる抜け道

画面上は2FAコードの入力が必須に見えていても、そのステップの後にあるページをURLから直接要求した場合にチェックを実施していなければ、処理の順番を飛ばせる。

これは認証フロー・ワークフローのサーバー側制御に関する問題。

### 6.3 他の機能への一般化

同様の「中間状態の検証不足」は、パスワード再設定、メールアドレス変更の確認、メール認証、購入確定、本人確認など、複数段階で処理される機能にも起こり得る。

ただし、これらの機能に今回のラボと同様の不備があるかは検証していない。

## 7. 推奨防止策と検知策

### 7.1 すべての保護リソースで2FA完了を検証する

`/my-account` のようなWebページだけでなく、保護されたAPIや重要操作でもサーバー側の認証状態を確認する。

認証途中のセッションは保護リソースを利用できない権限レベルに留める。

### 7.2 認証状態の遷移を厳密に実装する

`未認証 → 一次認証済み（2FA待ち）→ 完全認証済み` の状態を明確にし、正しいコードの検証が成功したときだけ完全認証へ遷移させる。

クライアント側の画面表示やURLだけを根拠に完了判定を行わない。

### 7.3 セッションの安全な取り扱い

認証レベルが変わるタイミングで必要に応じてセッション識別子を更新し、セッション固定などに対処する。ログアウトやタイムアウト時には状態を適切に無効化する。

### 7.4 重要操作の権限チェック

二要素認証を終えたセッションでも、操作対象の権限や本人確認が必要となる。保護ページへのアクセス可否と、個々のリソース操作の認可は別途検証する。

### 7.5 ログ監視

2FA未完了のセッションからの保護ページアクセス、コード検証失敗、一次認証直後の異常なページ遷移、重要操作の監査ログを記録し、不審な利用を検知する。

---

## 8. 実務上の想定被害

攻撃者が他人の一次認証情報を入手している場合、2FAを回避できるシステムでは不正ログインを阻止する最後の防壁が機能しなくなる可能性がある。

その結果、アカウント情報の閲覧、個人情報の流出、権限内での設定変更や不正操作などが生じ得る。

**今回はラボ上の `carlos` アカウントページを閲覧しSolvedを確認したのみであり、実在するユーザーへの被害やその他の機能への影響は実証していない。**

## 9. 検証の限界と未確認事項

- ブラウザが送受信した生のHTTPリクエスト・レスポンス
- `/my-account` への直接アクセス時のHTTPステータスとレスポンスヘッダー
- セッションCookie、サーバー側セッションデータの実装
- 認証途中と認証完了時のセッション識別子の変化
- 2FAコードの生成・保存・検証ロジック
- 認証フローの内部ソースコード
- アカウントページ以外の保護ページ・API・重要操作の挙動
- 他の利用者・実環境での再現性

画面で確認した事実と、認証処理の一般的な解釈・実務上のリスクを区別して記録した。

**結果：5/5問正解（100%）。全問「自信あり」。**

### 理解の整理

- 一次認証成功は、2FAを含むログイン完了と同義ではない。
- ブラウザのURLを直接指定できること自体は正常な機能。アクセス許可の判断はサーバーが行う。
- 2FA完了状態を保護ページ側でも確認することが、今回の根本対策。
- 認証以外でも、確認段階を踏むワークフローでは同様の不備が起こり得る。

## 11. 振り返りと次の学習課題

今回のラボではBurp Suiteを使わず、ブラウザ操作だけで一次認証と二要素認証の差を確認した。

正常な2FAフローで確認した `/my-account` に対し、別アカウントの2FA未完了状態から直接遷移してアカウントページを閲覧できたことが重要な証拠である。

今後は「セッションにはどのような認証状態が存在し、各ページ・APIが何を確認すべきか」を意識して学習する。
