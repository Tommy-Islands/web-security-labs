# Stored XSS：ブログのコメント機能におけるJavaScript実行の検証

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Stored XSS into HTML context with nothing encoded |
| 難易度 | Apprentice |
| 検証対象 | ブログのコメント投稿機能 |
| 脆弱性の種類 | Stored XSS（格納型クロスサイトスクリプティング） |
| 検証環境 | Parrot Security（VirtualBox） |
| 使用ツール | Burp Suite Community Edition / ブラウザ |
| 検証結果 | Solved |

### 検証目的

ブログのコメント投稿機能において、投稿した内容が保存・再表示されることを確認し、HTMLタグやJavaScriptが適切に処理されているか検証する。

また、Reflected XSSとの違いを理解し、Stored XSSが成立する原因と想定される被害を考察する。

## 2. 攻撃シナリオと背景

### 2.1 想定するシステム

一般利用者が記事を閲覧し、コメントを投稿できるブログサイトを想定する。

投稿されたコメントはサーバー側で保持され、記事ページを再度開いた際にも表示される。

コメント内容は、投稿者以外の利用者にも公開されるものとする。

### 2.2 攻撃者の目的

攻撃者は、コメント投稿機能に存在するStored XSSを悪用し、悪意あるJavaScriptをコメントとして保存させる。

その後、他の利用者が記事を閲覧した際に、利用者のブラウザ上でそのJavaScriptを実行させることを狙う。

### 2.3 想定される攻撃の流れ

**第1段階：コメントの保存機能を調査**

通常の文字列をコメントとして投稿し、ページを再読み込みしても内容が残るか確認する。

**第2段階：HTMLタグの解釈を調査**

HTMLタグを含むコメントを投稿し、ブラウザがタグを文字列として扱うか、HTML要素として解釈するか確認する。

**第3段階：JavaScriptの実行を検証**

JavaScriptを含むコメントを投稿し、記事ページでコードが実行されるか確認する。

**第4段階：第三者への影響（未検証）**

実際の攻撃では、保存された不正なコメントを含む記事を第三者が閲覧することで、第三者のブラウザでもJavaScriptが実行される可能性がある。

今回の検証では、第三者への攻撃や情報窃取は実施していない。

## 3. 検証手順と結果

### 3.1 通常コメントの投稿

まず、コメント投稿フォームへ通常の文字列を入力した。

**入力値**

```text
XSSTEST123
```

**結果**

- コメントが記事ページに表示された
- 記事ページを再読み込みしてもコメントが残っていた

この結果から、投稿内容がサーバー側で保持され、ページを再表示した際にも取得できる状態であることを確認した。

ただし、この段階ではHTMLやJavaScriptの実行可否までは判断できない。

### 3.2 HTMLタグの解釈確認

次に、コメント欄へHTMLタグを含む文字列を投稿した。

**入力値**

```html
<b>XSSTEST456</b>
```

**結果**

`XSSTEST456` が太字で表示された。

この結果から、投稿内容に含まれる `<b>` タグが、単なる文字列ではなくHTML要素として解釈されたと判断した。

本来、HTMLタグを許可しないコメント欄であれば、次のようにタグを文字列として表示することが望ましい。

```text
<b>XSSTEST456</b>
```

ただし、HTMLタグが解釈されることだけでは、JavaScriptが実行できることまでは証明できない。

### 3.3 JavaScript実行の検証（1回目）

コメント欄に以下の文字列を投稿した。

**入力値**

```html
<script>alert(atack!)</script>
```

**結果**

ダイアログは表示されなかった。

#### 原因の考察

JavaScriptの `alert()` に渡した `atack!` は、有効なJavaScriptの式ではない。

`!` はJavaScriptで論理否定に使用される演算子だが、この位置では正しい構文にならない。

したがって、JavaScriptの構文エラーによってスクリプトが正常に実行されなかったと考えられる。

ただし、ブラウザの開発者ツールでエラー内容を直接確認したわけではないため、構文エラーはコードに基づく推定原因として扱う。

この時点では、Stored XSSが防止されていると判断することはできない。

### 3.4 JavaScript実行の検証（2回目）

1回目の入力内容を見直し、表示する文字列をシングルクォートで囲んだ。

**修正後の入力値**

```html
<script>alert('Atack!')</script>
```

**結果**

- ブラウザに `Atack!` と表示されるダイアログが出現した
- PortSwiggerのラボがSolvedになった

JavaScriptが正常に実行されたことから、コメント投稿機能でStored XSSが成立することを確認した。

### 3.5 検証結果一覧

| 検証項目 | 入力内容 | 結果 |
|---|---|---|
| 通常のコメント投稿 | `XSSTEST123` | 表示された |
| コメントの保持 | ページ再読み込み | コメントが残存 |
| HTMLタグの解釈 | `<b>XSSTEST456</b>` | 太字で表示 |
| JavaScript実行（1回目） | `<script>alert(atack!)</script>` | ダイアログなし |
| JavaScript実行（2回目） | `<script>alert('Atack!')</script>` | ダイアログ表示・Solved |

## 4. 技術的な原因と考察

### 4.1 Stored XSSとは

Stored XSSは、攻撃者が入力したコードがアプリケーション側に保存され、そのデータを閲覧した利用者のブラウザで実行される脆弱性である。

典型的な入力箇所には、ブログのコメント欄、掲示板、プロフィールなどがある。

### 4.2 脆弱性が成立する仕組み

今回のラボでは、コメント欄に投稿したHTMLタグがブラウザによって解釈された。

さらに、修正したJavaScriptを投稿すると、ブラウザでダイアログが表示された。

この結果から、投稿されたコメントが安全に処理されず、HTMLとして解釈可能な形で出力されていたと考えられる。

例えば、サーバーが保存済みのコメントを次のように出力した場合を考える。

```html
<div class="comment">
    <script>alert('Atack!')</script>
</div>
```

ブラウザがこのHTMLを通常のページ読み込み時に受け取ると、`script` 要素を解釈してJavaScriptを実行する可能性がある。

※ このHTMLは仕組みを説明するための仮想例であり、実際のHTTPレスポンスから取得したコードではない。

### 4.3 根本原因

今回の脆弱性の根本原因は、保存されたユーザー入力を、HTMLの出力箇所に適した方法で安全に処理していないことと考えられる。

データベースに保存された情報であっても、安全なデータとは限らない。

外部から投稿されたコメントは、表示する段階でも信頼できない入力として扱う必要がある。

### 4.4 最初の失敗から学んだこと

今回、最初に試したJavaScriptではダイアログが表示されなかった。

しかし、入力内容を修正したところJavaScriptが実行された。

このことから、検証に失敗した際は、脆弱性対策によって遮断された可能性だけでなく、入力コード自体の文法や実行条件も確認する必要があると学んだ。

## 5. Reflected XSSとの比較

| 項目 | Reflected XSS | Stored XSS |
|---|---|---|
| 主な入力箇所 | 検索欄、URLパラメータ | コメント欄、投稿フォーム |
| 攻撃コードの保存 | 通常は保存されない | サーバー側で保存される |
| 実行のきっかけ | 細工されたリクエストへの応答を表示 | 保存された内容を含むページを表示 |
| 実行場所 | ページを表示した利用者のブラウザ | ページを表示した利用者のブラウザ |
| 第三者への攻撃 | 細工したURLへの誘導など | 悪意ある投稿を含むページの閲覧など |

いずれもブラウザ上でJavaScriptが実行される点は共通している。

違いは、攻撃コードがレスポンスへ到達する経路と、その保存の有無にある。

## 6. 想定される被害とリスク

### 6.1 今回実証した影響

- コメントが保存・再表示されること
- HTMLタグが解釈されること
- コメントを通じてJavaScriptが実行されること

### 6.2 想定される被害

実際のWebサイトでStored XSSが悪用された場合、以下の影響が考えられる。

- 偽ログインフォームなどによるフィッシング
- ページの表示内容の改ざん
- 利用者の権限で実行可能なサイト内操作の悪用
- JavaScriptからアクセス可能な情報の不正取得
- 複数の閲覧者への攻撃の拡大

ただし、実際の影響範囲はブラウザの制限、アプリケーションの実装、Cookie属性、利用者の権限などによって異なる。

### 6.3 検証範囲と限界

今回のラボでは、JavaScriptによるダイアログの表示まで確認した。

第三者のブラウザでの実行、認証情報の取得、Cookieの取得、不正なサイト内操作などは検証していない。

したがって、これらの被害が実際に成立することまでは証明していない。

## 7. 推奨対策

### 7.1 出力時の適切なHTMLエスケープ

投稿コメントをHTMLのテキスト部分へ出力する際は、特殊文字を適切にエスケープする。

例えば、次の入力値を考える。

```html
<script>alert('Atack!')</script>
```

HTMLのテキスト部分では、概念的に次のように出力する。

```html
&lt;script&gt;alert('Atack!')&lt;/script&gt;
```

これにより、ブラウザはスクリプト要素ではなく文字列として表示する。

なお、HTML属性、URL、JavaScriptなど、出力する場所によって必要なエスケープ処理は異なる。

### 7.2 安全なDOM操作

JavaScriptで投稿内容を画面へ表示する場合は、単なるテキスト表示であれば `textContent` を利用する。

**不適切な例**

```javascript
commentElement.innerHTML = comment;
```

**改善例**

```javascript
commentElement.textContent = comment;
```

`innerHTML` に信頼できない入力値を直接渡すと、HTMLとして解釈されるため危険な場合がある。

一方、`textContent` は文字列として挿入するため、コメントをテキスト表示する用途に適している。

ただし、今回のラボはサーバーから返されるHTMLに起因するため、サーバー側の出力処理を適切に修正することが重要である。

### 7.3 HTMLを許可する場合のサニタイズ

コメントに一部のHTMLタグを許可する仕様の場合は、信頼できるHTMLサニタイズライブラリを利用し、危険なタグや属性を除去する。

単純な文字列置換やブラックリストだけに依存しないことが重要である。

### 7.4 Content Security Policy（CSP）

適切なCSPを設定し、スクリプトの読み込み元や実行方法を制限する。

ただし、CSPは補助的な防御策であり、適切な出力処理を省略する理由にはならない。

### 7.5 Cookieの保護

必要に応じて `HttpOnly`、`Secure`、`SameSite` などのCookie属性を適切に設定する。

ただし、Cookieを保護してもXSS自体が解消されるわけではない。

## 8. 学習内容と振り返り

### 今回学んだこと

- Stored XSSでは投稿内容がサーバー側に保持される
- 保存されたコメントがブラウザでHTMLとして解釈される可能性がある
- HTMLタグの解釈とJavaScriptの実行は分けて確認する必要がある
- JavaScriptの構文エラーと、XSS対策による実行阻止を混同してはいけない
- Reflected XSSとStored XSSでは攻撃コードが利用者に届く経路が異なる
- 保存されたデータであっても、表示時には不信頼データとして扱う必要がある
- 脆弱性診断では実証した事実と想定される被害を区別する必要がある

### 理解度チェック

全5問を実施し、5問すべて正解した。

特に、Reflected XSSとStored XSSの比較問題では、攻撃コードの実行対象と実行タイミングについて、問題文の曖昧さを指摘した。

### 今後の課題

- JavaScriptの基本構文の理解を深める
- ブラウザの開発者ツールでJavaScriptのエラーを確認できるようになる
- HTMLの出力コンテキスト別のXSS対策を学ぶ
- DOM-based XSSを実際に検証する
- 実証結果を根拠に脆弱性の影響範囲を評価する
