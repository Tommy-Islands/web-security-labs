## 2. 実務上の攻撃シナリオ

### 2.1 想定するシステムと攻撃者

ECサイトの商品詳細画面で、サーバーが`/image?filename=...`の値を使って画像ファイルを読み込み、ユーザーへ返却していると想定する。

外部の利用者は商品画像を表示できるが、OSの設定ファイルやアプリケーションの内部ファイルへのアクセス権限は本来持たない。

### 2.2 攻撃から被害までの流れ

1. 攻撃者が画像リクエストの`filename`パラメータを特定する。
2. 通常の画像名の代わりに`../../../etc/passwd`などの相対パスを指定する。
3. サーバーが入力パスの安全性と読み取り可能範囲を適切に検証していない場合、画像ディレクトリ外へ移動してファイルを開いてしまう。
4. 対象ファイルの内容がHTTPレスポンスとして返却され、サーバー内の情報が漏えいする。
5. 実務では、権限次第で設定ファイル、ソースコード、ログなどから機密情報の流出につながるおそれがある。

### 2.3 想定被害・原因・対策の対応

| 観点 | 内容 |
|---|---|
| 実証した被害 | ラボの画像取得機能を通じて`/etc/passwd`の内容を閲覧 |
| 実務上の想定被害 | 設定ファイル、ソースコード、ログ、APIキー等の漏えい |
| 根本原因 | 外部入力のファイルパスを安全な領域に制限せず読み取りに使用している |
| 防止策 | 許可リスト方式、正規化・実体パス解決後の配置先検証、OS権限とディレクトリ範囲の制限 |
| 検知策 | `../`、エンコード済みの移動表現、異常なファイル参照、画像取得エラー等の監視 |

**実務上の漏えい対象は可能性の説明であり、今回のラボで`/etc/passwd`以外を取得した事実はない。**

## 3. 技術的背景

### 3.1 Path Traversalとは

Path Traversal（ディレクトリトラバーサル）は、アプリケーションが外部入力からファイルパスを組み立てる際、想定されたディレクトリより外側のファイルへアクセスできてしまう問題。

ブラウザがリクエストの`filename`を編集できること自体は正常。サーバーがファイルを開く前に許可範囲を確認する必要がある。

### 3.2 `../`の意味

`../`は、相対パスにおいて親ディレクトリを1階層表す。

`../../../`は通常、起点となるディレクトリから親へ3階層たどる。`etc/passwd`とつなげることで、Linuxの`/etc/passwd`を参照するようにパスを解決させられる場合がある。

実際にどこに到達するかは、読み取り処理の起点となるディレクトリの場所や実装によって異なる。

### 3.3 `/etc/passwd`の性質

Linux系OSの`/etc/passwd`は、ユーザー名やUID/GID、ホームディレクトリ、ログインシェルなどのアカウント情報を含むファイル。

現代のLinuxではパスワードハッシュは通常`/etc/shadow`へ格納されるため、**`/etc/passwd`を読み取ったことと平文パスワードを取得したことは同義ではない**。

今回のラボでは`root`、`peter`、`carlos`、`user`などのアカウント名が見えた。

## 4. 検証手順

### STEP 1：画像取得リクエストの確認

商品詳細ページを開き、Burp Suiteで画像読み込みのリクエスト`GET /image?filename=<ファイル名>.jpg`を確認した。

### STEP 2：Repeaterへ送信

画像取得のリクエストをBurp Repeaterへ送り、`filename`パラメータを編集できる状態にした。

### STEP 3：パスを改変

`filename`の値を画像ファイル名から次の値へ変更した。

```text
../../../etc/passwd
```

### STEP 4：リクエストを再送信

Repeaterから変更後のリクエストを送信し、レスポンスを確認した。

### STEP 5：サーバー内部ファイルの取得を確認

レスポンスには`/etc/passwd`の内容がそのまま返り、`root`、`peter`、`carlos`、`user`などのアカウント情報を確認できた。

**LAB Solvedを確認した。**

## 6. 検証結果と根本原因

| 項目 | 実際に確認した結果 |
|---|---|
| 入力パラメータ | 画像取得の`filename` |
| 改変値 | `../../../etc/passwd` |
| 使用機能 | Burp Suite Repeater |
| 返却されたデータ | `/etc/passwd`の内容（`root`、`peter`、`carlos`、`user`など） |
| 最終結果 | LAB Solved |

### 根本原因

サーバーが利用者の指定したファイル名を読み取り処理に使う際、想定された画像ディレクトリの外に出ないことを検証していないこと。

`../`のような移動表現を含む入力がサーバーのファイルシステム上で解決され、画像以外の内部ファイルを読み取れる状態になっていた。

## 7. 推奨防止策と検知策

### 7.1 許可リスト方式

可能ならクライアントから任意のファイルパスを受け取らず、**画像IDや許可済みファイル名をサーバー側の安全な保存先へ対応付ける**。

指定可能なファイルをサーバー側で限定し、入力値をそのままファイルシステムのパスに使用しない。

### 7.2 正規化・実体パス解決後のアクセス範囲検証

外部入力をどうしてもパスとして扱う必要がある場合は、パスの正規化と実体パスの解決を行い、最終的な参照先が許可ディレクトリ内に収まることを検証する。

単純な文字列の先頭一致や`../`の文字列除去だけでは不十分。区切り文字の違い、シンボリックリンク、エンコードなども考慮する。

### 7.3 最小権限と分離

Webアプリケーションの実行ユーザーが、不要な設定・秘密情報を読み取れないようにOS権限を制限する。画像ファイルの保存先と機密情報の保存先を適切に分離する。

### 7.4 ログ監視と異常検知

`filename`への階層移動文字列、想定外の拡張子、存在しないファイルへの大量の参照、通常の画像ではないファイルの配信などを監視する。

## 8. 実務上の想定影響

画像表示、PDFダウンロード、ログ表示、添付ファイル閲覧、バックアップ取得など、ファイルパスを外部入力で指定できる機能では同様の問題が起こり得る。

アプリケーションの実行ユーザーが読める範囲によって、設定情報、APIキー、データベース接続情報、ソースコード等の流出につながる可能性がある。

**今回は学習ラボ内の`/etc/passwd`取得を確認したのみで、これらのファイルや認証情報の漏えいは未検証。**

## 9. 未検証事項・制約

- 実際のBurp HTTPリクエスト・レスポンス全文
- 実際のHTTPステータス、レスポンスヘッダー、ファイル内容の完全な行
- サーバー側の画像ディレクトリの実際の配置とパス解決ロジック
- 対象OSやWebサーバーの詳細、アプリケーションの実行権限
- パスのURLエンコード、別の階層深さ、絶対パスなどの追加パターン
- シンボリックリンクや正規化の扱い
- `/etc/passwd`以外の設定ファイル・ログ・秘密情報へのアクセス可否
- 他の機能・実在システムへの影響

再構成HTTPは説明用であり、実際の通信原文を保存した証拠ではない。

### 理解の整理

- `../`は親ディレクトリを指し、入力の起点やパスの解決により想定外のファイルへ到達できる。
- 画像取得のような通常の機能も、外部から指定されるファイル名の扱い次第で脆弱性になり得る。
- 適切な対策は許可するファイルと読み取り範囲をサーバー側で制限すること。
- `/etc/passwd`の閲覧とパスワード自体の窃取は区別して説明する。
