# Business Logic Vulnerability：メールアドレス変更による管理者機能へのアクセス

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Inconsistent security controls |
| 難易度 | Apprentice |
| 分野 | Business Logic Vulnerabilities |
| 脆弱性 | アカウント情報の変更処理とアクセス制御の不整合 |
| 関連するセキュリティ概念 | Authentication / Authorization / Privilege Escalation |
| 使用ツール | Burp Suite Community Edition、Burp専用ブラウザ |
| 検証環境 | VirtualBox / Parrot Security |
| 検証結果 | Solved |
| 理解度チェック | 5問正解 / 5問（100%） |

### 検証目的

一般ユーザーがメールアドレスを変更することで、本来アクセスできない管理者機能を利用できるか検証する。

特に、アカウント登録時のメール認証と、登録後のメールアドレス変更処理におけるセキュリティ制御の不整合に注目する。

## 2. 攻撃シナリオ

### 2.1 対象システム

対象は、ユーザー登録、メール認証、ログイン、メールアドレス変更機能を備えた学習用Webアプリケーションである。

また、管理者専用の `/admin` ページが存在する。

初期状態で `/admin` にアクセスすると、次のメッセージが表示された。

```text
Admin interface only available if logged in as a DontWannaCry user
```

このメッセージから、管理者画面の利用にDontWannaCryユーザーであるという条件が関係していることが分かった。

### 2.2 攻撃者の目的

一般ユーザーとして登録したアカウントを利用し、管理者画面へアクセスして、ユーザー `carlos` を削除する。

### 2.3 着眼点

新規登録画面には、次の案内が表示されていた。

```text
If you work for DontWannaCry, please use your @dontwannacry.com email address
```

このことから、メールアドレスのドメインと管理者機能へのアクセス制御に関連がある可能性を考えた。

検証では、メール認証済みの一般ユーザーがメールアドレスを変更した場合、アクセス権限の判定が変わるかを調査した。

## 3. 公式Solutionとの相違点

PortSwiggerの公式Solutionでは、最初にBurp Suiteの次の機能を使用する。

`Target → Site map → Engagement tools → Discover content`

この機能で隠れたURLを探索し、`/admin` を発見する手順になっている。

しかし、今回使用したBurp Suite Community Editionでは、Discover contentを実行できなかった。

そのため、以下の工程を変更した。

| 公式Solution | 今回の実施内容 |
|---|---|
| Discover contentを開始 | Community Editionの機能制限により未実施 |
| 探索結果から `/admin` を発見 | 公式Solutionに記載された `/admin` を直接開いて確認 |
| 登録画面を調査 | 実施 |
| 一般ユーザーを登録・メール認証 | 実施 |
| メールアドレスを変更 | 実施 |
| 管理者機能へアクセスし、ユーザーを削除 | 実施 |

**URL探索工程のみを省略しており、それ以降の検証は公式Solutionと同じ攻撃シナリオに沿って実施した。**

したがって、今回の検証で `/admin` を独力で発見したとは主張しない。

## 4. 検証手順と観察結果

### STEP 1：管理者画面の初期状態を確認

Burp専用ブラウザで、次のパスにアクセスした。

```text
/admin
```

**確認結果**

```text
Admin interface only available if logged in as a DontWannaCry user
```

通常の状態では管理者画面を利用できず、DontWannaCryユーザーであることがアクセス条件として示された。

### STEP 2：新規登録画面を確認

画面右上の `Register` をクリックした。

登録画面には、DontWannaCryの社員は `@dontwannacry.com` のメールアドレスを使用するよう案内が表示されていた。

管理者機能のアクセス条件とメールアドレスのドメインに関係がある可能性を確認した。

### STEP 3：受信可能なメールアドレスで一般ユーザーを登録

ラボの `Email client` を開き、利用できるメールアドレスを確認した。

アドレスはラボ専用の `exploit-server.net` ドメインだった。

登録フォームに以下の情報を入力した。

| 項目 | 設定内容 |
|---|---|
| Username | `testuser` |
| Email | ラボのEmail clientで受信可能なアドレス |
| Password | 検証用パスワード |

この段階では `@dontwannacry.com` のアドレスを使用せず、一般ユーザーとして登録した。

### STEP 4：メール認証を完了

`Email client` に登録確認メールが届いた。

メールに記載された確認リンクをクリックし、アカウントの登録確認を完了した。

その後、作成したアカウント `testuser` でログインした。

**確認結果**

一般ユーザーとして正常にログインできた。

この時点で確認したメールアドレスの所有者であることと、DontWannaCryの社員であることは別の問題である。

### STEP 5：メールアドレスを変更

ログイン後、`My account` を開いた。

メールアドレス変更機能を使用し、次の値に変更した。

**変更後のメールアドレス**

```text
testuser@dontwannacry.com
```

変更後、アカウント画面にこのアドレスが表示された。

**確認結果**

- 変更先のメールアドレスがアカウントに反映された
- 変更先アドレスへの新たな確認メールによる認証を行わずに、次の検証へ進めた
- `@dontwannacry.com` のメールボックスを所有していることは証明していない

### STEP 6：管理者画面へのアクセスを検証

メールアドレス変更後、再び `/admin` にアクセスした。

**確認結果**

初回とは異なり、管理者画面が表示された。

画面には次のユーザーが表示されていた。

- `wiener`
- `carlos`
- `testuser`

各ユーザーに対する `Delete` リンクも表示されていた。

この結果から、メールアドレスの変更によって、以前は拒否されていた管理者画面へのアクセスが許可されるようになったことを確認した。

ただし、画面が表示されるだけでは、管理者操作が実際に成功するかは確定しない。

### STEP 7：管理者専用のユーザー削除を実行

管理画面に表示された `carlos` の `Delete` をクリックした。

**確認結果**

```text
User deleted successfully!
```

削除成功のメッセージが表示された。

さらに、ユーザー一覧から `carlos` が消えたことを確認した。

ラボのステータスも以下の表示に変化した。

```text
Congratulations, you solved the lab!
```

**最終結果：Solved**

一般ユーザーとして登録したアカウントから、管理者専用のユーザー削除機能を実行できた。

## 5. 検証結果の整理

| 検証項目 | 変更前・初期状態 | 変更後 |
|---|---|---|
| アカウント | 一般ユーザー `testuser` | 同じアカウント |
| メールアドレス | ラボ専用の受信可能なアドレス | `testuser@dontwannacry.com` |
| `/admin` へのアクセス | 拒否 | 許可 |
| 管理者用ユーザー一覧 | 閲覧できない | 閲覧できた |
| ユーザー削除 | 未実施 | `carlos` の削除に成功 |
| ラボ | Not solved | Solved |

### 実証できたこと

1. 一般ユーザーがアカウントのメールアドレスを変更できた。
2. 変更先メールアドレスの所有確認を完了しないまま、変更後のアドレスが反映された。
3. メールアドレス変更後に管理者画面へのアクセスが許可された。
4. 管理者専用のユーザー削除操作を実行できた。
5. `carlos` の削除成功が確認され、ラボがSolvedになった。

## 6. 脆弱性の根本原因

### 6.1 セキュリティ制御の不整合

今回の脆弱性は、**アカウント登録時とメールアドレス変更時で、セキュリティ上の前提が一貫していなかったこと**に起因すると考えられる。

新規登録時にはメールアドレスの所有確認が行われた。

一方、登録後にはユーザーが `@dontwannacry.com` のメールアドレスへ変更でき、その後、管理者画面へアクセスできるようになった。

このことから、一般ユーザーが操作可能なアカウント情報が、管理者機能へのアクセス制御に影響していたことが分かる。

### 6.2 AuthenticationとAuthorization

**Authentication（認証）**

ユーザーの身元を確認する処理。

例：ユーザー名・パスワードによるログインや、メールアドレスの所有確認。

**Authorization（認可）**

認証されたユーザーが、特定の機能や操作を実行してよいかを判断する処理。

例：管理画面へのアクセスやユーザー削除の許可。

今回、`testuser` は正常に認証された一般ユーザーだった。

問題は、そのユーザーがメールアドレスを変更することで、本来許可されない管理者操作を実行できたことである。

### 6.3 メールアドレスの所有確認と権限付与は別問題

仮に `@dontwannacry.com` のメールアドレスを実際に所有していると確認できた場合でも、それだけで管理者権限があるとは限らない。

企業のメールアドレスを持つ社員全員が管理者であるとは限らないため、管理者権限は適切な権限管理に基づいて付与する必要がある。

### 6.4 内部実装についての注意

今回の観察結果から、メールアドレスのドメインがアクセス判定に利用されていた可能性は高い。

ただし、サーバーのソースコードやデータベースは確認していない。

したがって、以下は断定できない。

- メールドメインをどのような条件式で照合しているか
- 管理者ロールが内部的に付与されたか
- セッション内の権限情報が変更されたか
- 管理画面へのアクセス判定が具体的にどこで実施されているか

**今回断定できるのは、メール変更後に管理者画面へアクセスでき、ユーザー削除が成功したという観察結果までである。**

## 7. 想定される影響

### 7.1 今回実証した影響

- 本来アクセスできない管理者画面へのアクセス
- 管理者用ユーザー一覧の閲覧
- 管理者専用のユーザー削除処理の実行
- 権限不足の一般ユーザーによる管理操作の実行

### 7.2 実際のシステムで想定される被害

同様の設計不備が存在する場合、次のようなリスクが考えられる。

- 管理者専用情報の不正閲覧
- ユーザー情報の不正変更や削除
- 本来許可されない管理機能の利用
- 管理対象データの破壊や業務停止
- 利用者情報の機密性・完全性の低下

ただし、今回実証した管理操作は `carlos` の削除である。

ほかの機能について同様の操作が可能であるとは断定しない。

## 8. 推奨対策

### 8.1 メールアドレス変更時にも所有確認を実施する

変更先メールアドレスへ確認リンクを送信し、その所有確認が完了してから変更を確定する。

登録時だけでなく、変更時にも一貫した検証を適用する。

### 8.2 管理者権限をメールアドレスだけで決定しない

管理者権限は、サーバー側で適切に管理された権限情報を用いて判定する。

メールアドレスやそのドメインは、管理者権限を自動的に保証するものとして扱わない。

### 8.3 管理者機能へのアクセスをサーバー側で認可する

管理画面の表示だけでなく、ユーザー削除などの個別の操作でも権限を検証する。

フロントエンドのリンク表示制御だけに依存しない。

### 8.4 権限に影響する属性変更を適切に管理する

メールアドレス、組織所属、ロールなど、権限判定に関係する属性については、変更経路ごとに認可・検証・監査を実施する。

### 8.5 権限変更やアカウント更新のテストを行う

以下の観点で検証する。

- 新規登録時とメール変更時の検証が一貫しているか
- 未確認のメールアドレスで特権機能を利用できないか
- 一般ユーザーが管理者機能を直接実行できないか
- アカウント情報の変更によって想定外の権限が付与されないか

## 9. 検証の限界と未確認事項

今回の検証では、以下は確認していない。

- Discover contentによる `/admin` の発見
- サーバー内部の認可処理
- 管理者ロールの内部的な変更有無
- `@dontwannacry.com` 以外のドメインに対する判定
- 別のユーザーアカウントでも同様の現象が起きるか
- ユーザー削除以外の管理者機能への影響
- 実際の企業システムに同様の問題が存在するか

また、メールアドレスの変更時に所有確認の処理が内部でどのように実装されているかは調査していない。

今回確認したのは、**変更先メールアドレスの所有確認を完了しないまま、変更後の管理者機能へのアクセスとユーザー削除が成立したこと**である。

### 10.2 理解できたこと

- アカウント情報の変更とアクセス制御の不整合
- 新規登録時とメール変更時のセキュリティ検証の違い
- メールアドレスの所有確認と管理者権限の違い
- AuthenticationとAuthorizationの違い
- 管理画面へのアクセスと管理者操作の実行を区別する必要性
- 観察した事実と内部実装の推測を区別する重要性

### 10.3 客観的な理解度評価

今回の選択式問題では全問正解し、すべて自信ありと回答した。

基本的な認証・認可の概念や、今回の脆弱性の成立条件については理解できていると考えられる。

ただし、公式Solutionを参照して進めたため、未知のアプリケーションから同様の脆弱性を独力で発見できるかは未評価である。

### 10.4 復習課題

1. AuthenticationとAuthorizationの違いを、自分の言葉で説明する。
2. メールアドレスの所有確認が、管理者権限の証明にならない理由を説明する。
3. アカウント登録、メールアドレス変更、権限変更の各処理で必要なセキュリティ対策を整理する。
4. 管理画面へのアクセスと管理者操作の実行について、証拠の違いを説明する。
5. Burp Suiteを用いた隠しURL・管理機能の探索手法を別途学習する。

## 11. 今回の学習成果

今回のラボでは、特殊な攻撃コードを使用せず、通常のアカウント管理機能を操作することで管理者機能を利用できた。

重要だったのは、メールアドレス変更という正常な機能が、アクセス権限の判定と組み合わさることで脆弱性になっていた点である。

脆弱性は個々の機能だけでなく、**複数の機能が連携する際の前提や検証条件の不一致によって発生する**ことを学んだ。
