# Business Logic Vulnerability：クーポンの再利用制限を回避した不正購入

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Flawed enforcement of business rules |
| 難易度 | Apprentice |
| 分野 | Business Logic Vulnerabilities |
| 脆弱性 | クーポンの重複適用を防止する業務ルールの不備 |
| 使用環境 | VirtualBox / Parrot Security |
| 使用ブラウザ | Burp Suite付属ブラウザ |
| 検証方法 | Web画面からのクーポン適用操作 |
| 検証結果 | Solved |
| 理解度チェック | 5問正解 / 5問（100%） |

### 検証目的

ECサイトにおいて、割引クーポンを繰り返し適用することで、本来許可されない重複割引が発生するかを検証する。

特に、同じクーポンを連続して入力した場合と、異なるクーポンを交互に入力した場合の挙動を比較する。

最終的に、通常価格では購入できない商品を、割引ルールの不備を利用して購入できるか確認する。

---

## 2. 攻撃シナリオ

### 2.1 対象システム

対象は、ストアクレジットで商品を購入できる学習用ECサイトである。

検証用アカウントには、$100.00のストアクレジットが付与されていた。

今回の購入対象は以下の商品である。

| 項目 | 内容 |
|---|---|
| 商品名 | Lightweight l33t leather jacket |
| 通常価格 | $1,337.00 |
| ストアクレジット | $100.00 |

通常価格ではストアクレジットが不足するため、購入できない。

### 2.2 利用可能なクーポン

対象サイトでは、2種類の割引クーポンを確認できた。

| クーポンコード | 入手方法 | 確認した割引 |
|---|---|---|
| `NEWCUST5` | ホーム画面の新規顧客向け案内 | $5.00 |
| `SIGNUP30` | ニュースレター登録 | $401.10（通常価格の30%相当） |

### 2.3 攻撃者の目的

クーポンの再利用制限を回避して割引を繰り返し適用し、商品の合計金額を購入可能な範囲まで引き下げる。

### 2.4 攻撃の着眼点

ECサイトには、同じクーポンを複数回使用できないようにする制御が存在する。

しかし、その制御が適用順序によって回避できる場合、通常は認められない割引を重複して受けられる可能性がある。

今回は以下の2パターンを比較した。

- 同じクーポンを連続して入力する
- 異なるクーポンを挟んで再入力する

## 3. 検証手順と観察結果

### STEP 1：一般ユーザーでログイン

PortSwiggerが提供する学習用アカウントでログインした。

- Username：`wiener`
- Password：`peter`

ログイン後、ストアクレジットが$100.00であることを確認した。

### STEP 2：1つ目のクーポンを確認

ホーム画面に次の案内が表示されていた。

```text
New customers use code at checkout: NEWCUST5
```

この案内から、新規顧客向けのクーポン `NEWCUST5` を確認した。

### STEP 3：ニュースレターに登録

ホーム画面下部のニュースレター登録欄から、テスト用メールアドレスを使用して登録した。

ニュースレター登録特典として、2つ目のクーポン `SIGNUP30` を取得した。

### STEP 4：革ジャンをカートに追加

「Lightweight l33t leather jacket」を1個カートに追加した。

**カートの状態**

| 項目 | 金額 |
|---|---:|
| 商品価格 | $1,337.00 |
| クーポン割引 | $0.00 |
| 注文合計 | $1,337.00 |

ストアクレジットは$100.00であり、通常価格では購入できない状態だった。

### STEP 5：2種類のクーポンを適用

カートのクーポン入力欄で、次の順に適用した。

1. `NEWCUST5`
2. `SIGNUP30`

**適用結果**

| 項目 | 金額 |
|---|---:|
| 通常価格 | $1,337.00 |
| NEWCUST5 | -$5.00 |
| SIGNUP30 | -$401.10 |
| **合計** | **$930.90** |

`SIGNUP30` の割引額は通常価格$1,337.00の30%と一致していた。

```text
1,337.00 × 0.30 = 401.10

1,337.00 - 5.00 - 401.10 = 930.90
```

2種類のクーポンが同じ注文に適用できることを確認した。

### STEP 6：同一クーポンの連続使用を検証

`SIGNUP30` を適用した直後に、同じ `SIGNUP30` をもう一度入力した。

**確認結果**

```text
Coupon already applied
```

クーポンがすでに適用されているという警告が表示され、追加の割引は受けられなかった。

この結果から、少なくとも同一クーポンを連続して入力した場合には、再利用を拒否する制御が存在することを確認した。

### STEP 7：異なるクーポンを挟んで再利用

次に、直前の `SIGNUP30` とは異なる `NEWCUST5` を入力した。

**確認結果**

一度使用済みだった `NEWCUST5` を再び適用できた。

カートの合計金額も次のように変化した。

| 項目 | 金額 |
|---|---:|
| 変更前 | $930.90 |
| NEWCUST5の再適用 | -$5.00 |
| **変更後** | **$925.90** |

この結果から、同じクーポンの連続使用は拒否する一方、異なるクーポンを挟むと使用済みのクーポンを再利用できることが分かった。

### STEP 8：クーポンを交互に繰り返し適用

さらに、以下の2種類のクーポンを交互に入力した。

```text
NEWCUST5
SIGNUP30
NEWCUST5
SIGNUP30
...
```

検証では、最終的に各クーポンを4回ずつ適用できた。

**割引表示の集計**

| クーポン | 適用回数 | 1回あたりの割引 | 合計 |
|---|---:|---:|---:|
| NEWCUST5 | 4回 | $5.00 | $20.00 |
| SIGNUP30 | 4回 | $401.10 | $1,604.40 |
| **合計** | **8回** | | **$1,624.40** |

表示された割引額の合計が、商品の通常価格$1,337.00を上回った。

**カート画面では、注文合計が$0.00になっていた。**

なお、表示された割引額の合計と商品価格との差額は-$287.40だが、カートの最終合計には-$287.40ではなく$0.00と表示された。

この挙動の内部的な計算方法は未確認である。

### STEP 9：注文を確定

カートの合計金額が$0.00であることを確認し、`Place order` をクリックした。

**注文完了画面**

```text
Your order is on its way!
Total: $0.00
```

購入前後のストアクレジットは以下のとおりだった。

| 項目 | 金額 |
|---|---:|
| 購入前の残高 | $100.00 |
| 注文合計 | $0.00 |
| 購入後の残高 | $100.00 |

注文完了画面が表示され、ラボのステータスも `Solved` に変化した。

**通常価格$1,337.00の商品を、クーポンの重複適用によって合計$0.00で注文できたことを確認した。**

## 4. 検証結果の整理

今回確認した挙動をまとめる。

| 検証項目 | 結果 |
|---|---|
| 異なる2種類のクーポンの併用 | 成功 |
| 同一クーポンの連続使用 | 拒否 |
| 別クーポンを挟んだ再利用 | 成功 |
| 同一クーポンの複数回適用 | 成功 |
| 注文合計$0.00への変更 | 成功 |
| $0.00での注文確定 | 成功 |
| ストアクレジットの減少 | なし |
| ラボのクリア | Solved |

### 実証したこと

1. 同じクーポンを連続入力した場合には拒否される。
2. 異なるクーポンを間に挟むことで、使用済みクーポンを再利用できる。
3. 再利用による割引がカートの合計金額に反映される。
4. 2種類のクーポンを交互に各4回適用し、注文合計を$0.00にできた。
5. 割引後の金額で注文が成立し、残高が減少しなかった。

## 5. 脆弱性の根本原因

### 5.1 ビジネスルールの適用不備

今回の問題は、クーポンの重複利用を防ぐ業務ルールが一貫して適用されていなかったことである。

同一コードの連続使用は拒否されるにもかかわらず、別のクーポンを挟むと再利用できた。

本来、1注文につき1回のみ利用できるクーポンであれば、入力順序に関係なく重複適用を防ぐ必要がある。

### 5.2 考えられる内部的な原因

今回の挙動から、直前に適用されたクーポンと新たに入力されたクーポンだけを比較している可能性が考えられる。

例えば、次のような処理である。

```javascript
// 仮説を説明するための擬似コード
if (newCoupon === lastCoupon) {
  return "Coupon already applied";
}

applyCoupon(newCoupon);
```

この場合、直前のクーポンと異なるコードを入力すると、過去に使用済みのコードであっても適用できてしまう可能性がある。

**ただし、このコードは説明用の仮説であり、実際のラボのソースコードではない。**

サーバー内部の実装は確認していないため、原因となる具体的な条件式やデータ構造までは断定しない。

### 5.3 今回のBusiness Logic Vulnerabilityの特徴

今回の検証では、SQLインジェクションやXSSのような特殊な入力を使用していない。

通常のクーポン入力機能を、順序を変えて繰り返し使用しただけで不正な割引が成立した。

このように、正常な機能を組み合わせた結果、想定外の業務処理が成立することが、ビジネスロジックの脆弱性の特徴の一つである。

## 6. 想定される被害と影響

### 6.1 今回実証した影響

- 同一クーポンの再利用制限を回避できた
- 割引額を重複して適用できた
- 高額商品の注文合計を$0.00に変更できた
- ストアクレジットを消費せずに注文できた

### 6.2 実際のECサイトで想定される被害

同様の不備が存在する場合、以下の被害が考えられる。

- 割引クーポンの不正な重複利用
- 想定外の大幅値引きや無料購入
- 売上や利益の損失
- クーポン施策の予算超過
- 不正注文に伴う運用・調査負荷
- 請求金額と販売価格の不整合

これらは想定されるリスクであり、今回のラボですべてを実証したわけではない。

## 7. 推奨対策

### 7.1 適用済みクーポン全体を確認する

サーバー側で注文に適用されたクーポンの一覧を管理する。

新しいクーポンを受け取った際は、直前のコードだけでなく、注文全体の適用履歴に対して重複判定を行う。

```javascript
// 対策の概念を示す擬似コード
if (appliedCoupons.includes(newCoupon)) {
  return "Coupon already applied";
}

appliedCoupons.push(newCoupon);
```

実際にはクーポンごとの利用可能回数や併用条件に合わせて検証を行う。

### 7.2 注文確定時にも割引条件を検証する

クーポン入力時だけでなく、`Place order` に相当する注文確定処理でも次の項目を検証する。

- クーポンが有効か
- 利用回数の上限を超えていないか
- 同じ注文に重複適用されていないか
- 複数クーポンの併用が許可されているか
- 注文合計が正しく計算されているか

### 7.3 サーバー側で割引金額を再計算する

クライアント側に表示された金額だけに依存せず、サーバー側の信頼できる商品価格と割引ルールに基づいて金額を計算する。

### 7.4 操作順序を変えたテストを実施する

クーポン処理では、単独利用だけでなく、以下のような組み合わせを検証する。

- 同じクーポンを連続使用する
- 異なるクーポンを交互に使用する
- 一度適用したクーポンを削除して再適用する
- 割引の適用順序を入れ替える
- 利用上限を超える回数を指定する
- 割引額が商品価格を上回る組み合わせを試す

これらは今後のテスト観点であり、今回すべてを実施したわけではない。

## 8. 検証の限界と未確認事項

今回の検証では、以下は確認していない。

- サーバー内部のクーポン重複判定処理
- 適用済みクーポンの保存方法
- 合計金額が$0.00で表示される内部的な計算方法
- 割引額の計算が内部で実行される順序
- ほかの商品でも同様に無料購入できるか
- ほかのクーポンの組み合わせでも成立するか
- 別のアカウントでも再現できるか
- 実際の企業システムにも同様の不備が存在するか

**今回実証したのは、指定された学習用ECサイトで2種類のクーポンを交互に使用し、対象商品を$0.00で注文できたことまでである。**

## 10. 今回の学習成果

今回のラボでは、リクエストのパラメータを書き換えるのではなく、Webアプリケーションが提供する通常の機能を組み合わせて攻撃を成立させた。

クーポン自体には再利用を拒否する仕組みが存在していたが、異なるクーポンを挟むことでその制限を回避できた。

この結果から、**個々の機能に検証処理が存在していても、操作順序や複数機能の組み合わせによって業務ルールが破綻することがある**と学んだ。

今後は、単一の入力値だけでなく、操作の順序・回数・組み合わせにも注目して脆弱性を検証していく。
