# Business Logic Vulnerability：クライアント側の価格改変による不正購入

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Excessive trust in client-side controls |
| 難易度 | Apprentice |
| 分野 | Business Logic Vulnerabilities |
| 脆弱性 | クライアント側の価格情報を過剰に信用する不備 |
| 使用ツール | Burp Suite Community Edition |
| 使用機能 | Proxy / HTTP history、Repeater |
| 実行環境 | VirtualBox / Parrot Security |
| 検証結果 | Solved |
| 理解度チェック | 4/5問正解（80%） |

### 検証目的

ECサイトのカート追加処理において、ブラウザから送信する商品価格を改変することで、本来の販売価格とは異なる金額で購入できるか検証する。

PortSwiggerの公式解法に従い、Burp SuiteのRepeaterを使用してHTTPリクエストを編集し、購入処理への影響を確認した。

## 2. 攻撃シナリオと背景

### 2.1 想定するシステム

ECサイトでは、利用者が商品をカートに追加し、ストアクレジットを使用して購入できる。

商品の販売価格は本来、サーバー側の信頼できる商品情報に基づいて決定される必要がある。

しかし、今回のラボでは、商品をカートに追加する際のHTTPリクエストに、商品の価格を示す `price` パラメータが含まれていた。

### 2.2 攻撃者の目的

攻撃者は、通常価格では購入できない商品について、ブラウザから送信する価格を改変し、本来より安い金額で購入することを狙う。

今回の対象商品は、通常価格$1,337.00の「Lightweight l33t leather jacket」である。

### 2.3 攻撃シナリオ

1. 攻撃者が一般ユーザーとしてログインする。
2. 通常価格ではストアクレジット不足となることを確認する。
3. 商品をカートへ追加するHTTPリクエストを調査する。
4. `price` パラメータを本来の価格より低い値へ変更する。
5. 改変したリクエストをサーバーへ送信する。
6. カートの金額が変更されたか確認する。
7. 変更後の価格で注文が成立するか検証する。

## 3. 検証手順と結果

### STEP 1：一般ユーザーでログイン

PortSwiggerが提供する以下の学習用アカウントを使用した。

- Username：`wiener`
- Password：`peter`

ログイン後、利用可能なストアクレジットが$100.00であることを確認した。

### STEP 2：通常価格での購入を試行

対象商品の「Lightweight l33t leather jacket」をカートへ追加した。

通常価格は以下のとおりだった。

**$1,337.00**

その後、`Place order` をクリックして購入を試行した。

**確認結果**

`Not enough store credit for this purchase`

ストアクレジットが不足しているため、通常価格では購入できなかった。

### STEP 3：カート追加時のHTTPリクエストを確認

Burp Suiteで次の画面を開いた。

`Proxy → HTTP history`

商品をカートへ追加した際の `POST /cart` を確認した。

リクエスト本文には以下のパラメータが存在していた。

```text
productId=1&redir=PRODUCT&quantity=1&price=133700
```

各パラメータの意味は以下のとおり。

| パラメータ | 内容 |
|---|---|
| `productId=1` | 対象商品ID |
| `redir=PRODUCT` | リダイレクト先の指定 |
| `quantity=1` | 数量1 |
| `price=133700` | 商品価格を示す値 |

`price=133700` は、画面上の$1,337.00に対応しており、価格がセント単位で表現されていると考えられる。

この段階では、価格を送信していることは確認できたが、サーバーが改変された価格を受け入れるかは未検証だった。

### STEP 4：Repeaterで価格を改変

HTTP historyの `POST /cart` を右クリックし、`Send to Repeater` を選択した。

Repeaterでリクエスト本文の `price` のみを変更した。

**変更前**

```text
productId=1&redir=PRODUCT&quantity=1&price=133700
```

**変更後**

```text
productId=1&redir=PRODUCT&quantity=1&price=100
```

`price=100` は$1.00に相当する。

その他のパラメータは変更せず、Repeaterの `Send` をクリックした。

### STEP 5：HTTPレスポンスを確認

サーバーから次のレスポンスが返された。

```http
HTTP/2 302 Found
Location: /product?productId=1
X-Frame-Options: SAMEORIGIN
Content-Length: 0
```

`302 Found` はリダイレクトを示している。

**この時点では、価格改変の成功は確定していない。**

そのため、次にブラウザ上のカートを確認した。

### STEP 6：カートに反映された金額を確認

Burp専用ブラウザでカートを開き直したところ、次の状態になっていた。

| 項目 | 確認結果 |
|---|---:|
| 商品 | Lightweight l33t leather jacket |
| 単価 | $1.00 |
| 数量 | 2 |
| 合計金額 | $2.00 |

通常価格で追加した商品がすでにカートに存在していたため、検証後の数量は2個になっていた。

カート上では単価が$1.00として表示され、合計が$2.00に変化した。

**この結果から、クライアント側で改変した `price` がカートの金額に反映されたことを確認した。**

### STEP 7：改変後の価格で注文

カートの合計金額が$2.00であることを確認し、`Place order` をクリックした。

**確認結果**

```text
Your order is on its way.
Total: $2.00
```

注文完了画面が表示された。

さらに、ストアクレジットが以下のように変化した。

| 項目 | 金額 |
|---|---:|
| 購入前の残高 | $100.00 |
| 購入後の残高 | $98.00 |
| 差引金額 | $2.00 |

ラボのステータスも `Solved` に変化した。

これにより、通常価格では購入できなかった商品を、改変後の価格で注文できたことが確認された。

## 4. 注文完了画面で確認した不整合

購入完了画面では、以下の表示が確認された。

| 項目 | 表示 |
|---|---:|
| 商品欄の通常単価 | $1,337.00 |
| 数量 | 2 |
| 注文合計 | $2.00 |
| ストアクレジットの減少額 | $2.00 |

商品欄には通常価格が表示されている一方で、注文合計は改変後の価格で計算されていた。

### 実際に確認できたこと

- 商品欄の単価と注文合計に不一致がある
- 合計$2.00で注文が成立した
- ストアクレジットから$2.00が差し引かれた

### 考えられる原因

商品欄と注文合計が、異なる価格情報を参照している可能性が考えられる。

例えば、商品欄には商品マスタの通常価格が表示され、注文合計にはカートに保存された価格が使用されている可能性がある。

ただし、サーバー側のソースコードやデータ構造を確認していないため、**この内部的な仕組みは仮説であり、確定した事実ではない。**

## 5. 根本原因と技術的な考察

### 5.1 根本原因

本ラボの根本原因は、**クライアントから送信された商品価格をサーバー側で適切に検証せず、購入処理に利用していたこと**である。

HTTPリクエストに含まれるパラメータは、Burp Suiteなどのツールを使用して変更できる。

そのため、クライアント側の価格情報を信用してはいけない。

### 5.2 問題のある実装例

以下は考え方を示す擬似コードであり、実際のラボのソースコードではない。

```javascript
const productId = request.body.productId;
const quantity = request.body.quantity;
const price = request.body.price;

const total = price * quantity;
```

この実装では、利用者が送信した価格をそのまま計算に使っている。

### 5.3 正しい実装の考え方

販売価格はサーバー側の信頼できる商品情報から取得する。

```javascript
const productId = request.body.productId;
const quantity = request.body.quantity;

const product = getProductFromDatabase(productId);

const total = product.price * quantity;
```

実際には数量、割引、税金、配送費なども含め、最終的な請求金額をサーバー側で検証する必要がある。

### 5.4 Business Logic Vulnerabilityとの関係

今回の攻撃では、SQLインジェクションやXSSのような特殊な構文を使用していない。

通常のカート追加機能が処理する値を変更することで、購入金額を不正に操作できた。

これは、業務処理において本来守るべきルールが適切に強制されていない、ビジネスロジックの脆弱性である。

## 6. 想定される被害とリスク

### 6.1 今回実証した影響

- クライアント側で商品の価格パラメータを改変できた
- 改変後の価格がカートに反映された
- 通常価格より低い金額で注文できた
- ストアクレジットが改変後の注文合計に基づいて減算された

### 6.2 実際のECサイトで想定される被害

同様の脆弱性が実際のECサイトに存在した場合、以下のような被害につながる可能性がある。

- 商品の不正な値引き購入
- 売上や利益の損失
- 請求金額の不整合
- 不正注文への対応による運用負荷
- 顧客や取引先からの信用低下

### 6.3 検証範囲と限界

今回確認したのは、ラボで指定された商品の価格を$1.00に改変し、2個を合計$2.00で注文できたことまでである。

以下については未検証である。

- ほかの商品でも同様の価格改変が成立するか
- マイナス価格が受け入れられるか
- 価格を0にした場合の挙動
- ストアクレジットを不正に増加させられるか
- 実際の企業システムに同様の脆弱性が存在するか

未検証の影響が成立するとは断定しない。

## 7. 推奨対策

### 7.1 サーバー側で商品価格を決定する

クライアントから送られる価格を購入金額の根拠にせず、サーバー側の商品情報から販売価格を取得する。

### 7.2 注文確定時にも金額を検証する

カート追加時だけでなく、注文確定時にも商品の価格・数量・割引・合計金額を検証する。

### 7.3 信頼できない入力を前提とする

ブラウザから送信されるパラメータは利用者が変更可能であることを前提に設計する。

### 7.4 想定外の値を検証する

価格や数量について、0、負数、極端に大きな数値などを指定した場合の挙動を検証する。

ただし、単純な数値範囲チェックだけでは、正しい販売価格を保証できないため、サーバー側の価格決定と組み合わせる必要がある。

### 7.5 価格と請求金額の整合性を確認する

商品表示、カート、注文確定、ストアクレジット減算などの処理で、価格が一貫しているか確認する。

## 8. 理解度チェック

ラボ攻略後、全5問の理解度チェックを実施した。

### 8.1 結果

| 問題 | テーマ | 回答 | 判定 | 自信度 |
|---|---|---|---|---|
| Q1 | 価格改変の根本原因 | B | 正解 | 自信あり |
| Q2 | サーバー側の価格検証 | C | 正解 | 自信あり |
| Q3 | 302 Foundの意味 | B | 正解 | 自信あり |
| Q4 | 注文画面の価格不整合 | B | 正解 | 自信あり |
| Q5 | 実証結果と想定被害 | C | 不正解（正解D） | 自信あり |

**最終結果：5問中4問正解（80%）**

### 8.2 理解できたこと

- クライアントから送られた価格を信用することの危険性
- 商品価格をサーバー側で決定する必要性
- `302 Found` だけでは価格改変の成功を判断できないこと
- 商品欄と注文合計の不整合について、内部原因を断定してはいけないこと

### 8.3 誤答から判明した課題

**Q5：実証結果と想定被害**

商品欄に通常価格が表示されていたことから、価格改変は表示上の問題にとどまると判断してしまった。

しかし、実際には注文が成立し、ストアクレジットが$2.00減少していた。

つまり、画面表示だけでなく購入処理自体に影響が及んでいた。

この問題は自信ありで誤答したため、優先的に復習する。

### 8.4 総合評価

価格改変の仕組みとサーバー側の検証方法については基礎的な理解を確認できた。

一方、画面表示と実際の業務処理の結果が食い違う場合に、複数の証拠を総合して判断する力には改善の余地がある。

## 9. 学習内容と今後の課題

### 9.1 今回習得した操作

- Burp SuiteのHTTP historyから対象リクエストを探す
- `POST /cart` のパラメータを確認する
- Repeaterにリクエストを送る
- `price` パラメータを編集する
- 改変リクエストを再送信する
- HTTPレスポンスを確認する
- ブラウザのカートで実際の反映結果を確認する
- 注文完了と残高の変化を証拠として判断する

### 9.2 今後の課題

1. 画面表示・注文処理・残高の関係を整理する。
2. HTTPレスポンスと業務処理の成功を区別する。
3. ビジネスロジックの脆弱性における入力値の境界条件を学ぶ。
4. サーバー側の価格計算・検証処理を理解する。
5. 実証した影響と未検証のリスクを区別して報告する。
