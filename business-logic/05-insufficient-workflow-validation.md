# Business Logic Vulnerability：購入フローの検証不足による注文処理の回避

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Insufficient workflow validation |
| 難易度 | Practitioner |
| 分野 | Business Logic Vulnerabilities |
| 脆弱性 | 購入フローの検証不足 |
| 使用ツール | Burp Suite Community Edition |
| 使用機能 | Proxy / HTTP history、Repeater |
| 検証環境 | VirtualBox / Parrot Security |
| 検証結果 | Solved |
| 理解度チェック | 5問正解 / 5問（100%） |

### 検証目的

ECサイトの購入処理において、正規の注文確定処理を省略し、注文完了用のHTTPリクエストを直接送信することで、購入制限を回避できるか検証する。

特に、サーバーが購入処理の順序や状態を適切に検証しているかに着目した。

本検証はPortSwiggerの公式Solutionに沿って実施した。

---

## 2. 攻撃シナリオと実務上の影響

### 想定システムと攻撃者の目的

ストアクレジットで商品を購入できるECサイトを想定する。一般会員の攻撃者は、注文確定処理と注文完了処理が別々のHTTPリクエストになっていることを知る。

### 悪用から想定被害に至る流れ

攻撃者は保有残高より高額な商品をカートに入れ、残高確認や代金減算を行うはずの購入確定処理を通らず、注文完了用リクエストだけを送信する。サーバーが注文状態を確かめず後続処理を受け付ける場合、決済済みでない注文を完了扱いにできる可能性がある。これが受注・発送システムにも反映されるなら、未払い商品の発送、在庫損失、注文と決済の不整合が起こり得る。

### 根本原因・防止策・検知策

**根本原因：** 前の工程が正常終了したことをサーバー側で検証せずに後続処理を実行できること。**防止策：** 注文の状態遷移をサーバーで厳格に管理し、残高確認・減算・確定を整合性ある処理として扱う。注文完了ページのGETは確定済み注文の表示に限定する。**検知策：** 決済記録のない完了注文、未確定注文への完了処理、残高と注文額の不整合を監査する。

### 今回のラボで実証した範囲

高額な革ジャン（$1,337）を追加後、`POST /cart/checkout` を実行せずに `GET /cart/order-confirmation?order-confirmed=true` を直接送信した。Solved、カートが空、残高$8.26のままを確認した。内部注文レコード・発送は未確認。

## 3. 検証手順と結果

### STEP 1：一般ユーザーでログイン

PortSwiggerが提供する学習用アカウントでログインした。

- Username：`wiener`
- Password：`peter`

ログイン後、ストアクレジットが$100.00であることを確認した。

### STEP 2：安価な商品を通常購入

正常な購入時のHTTP通信を調べるため、以下の商品を購入した。

**Hexbug Battleground Tarantula Double Pack**

- 価格：$91.74
- 数量：1個

ブラウザ上で通常どおり商品をカートに追加し、`Place order` をクリックした。

注文完了画面に以下のメッセージが表示された。

```text
Your order is on its way!
```

購入前後のストアクレジットは以下のとおり。

| 項目 | 金額 |
|---|---:|
| 購入前の残高 | $100.00 |
| 商品価格 | $91.74 |
| 購入後の残高 | $8.26 |

通常の購入では、商品の代金がストアクレジットから差し引かれることを確認した。

### STEP 3：HTTP historyで購入フローを調査

Burp Suiteで次の画面を開いた。

`Proxy → HTTP history`

正常購入時の通信を確認したところ、次の順序でHTTPリクエストが記録されていた。

**① 注文確定処理**

```http
POST /cart/checkout HTTP/2
```

HTTPステータス：

```http
303 See Other
```

**② 注文完了ページへのアクセス**

```http
GET /cart/order-confirmation?order-confirmed=true HTTP/2
```

HTTPステータス：

```http
200 OK
```

正常購入では、`POST /cart/checkout` の後に、注文完了ページへのGETリクエストが発生していた。

この結果から、注文完了用のGETリクエストを直接送信した場合の挙動を検証することにした。

### STEP 4：注文完了リクエストをRepeaterに保存

HTTP historyで次のリクエストを選択した。

```http
GET /cart/order-confirmation?order-confirmed=true HTTP/2
```

右クリックして `Send to Repeater` を選択した。

この段階では、リクエストの内容を変更せず、後から再送信できる状態にした。

**注意事項**

PortSwigger公式Solutionでは、パラメータ名が `order-confirmation=true` と記載されている。

一方、今回のラボインスタンスで実際に取得できたリクエストは `order-confirmed=true` だった。

本レポートでは、実際に観察・送信したリクエストを記録している。

### STEP 5：高額商品をカートに追加

Burp専用ブラウザで商品一覧に戻り、次の商品をカートに追加した。

**Lightweight l33t leather jacket**

| 項目 | 値 |
|---|---:|
| 商品価格 | $1,337.00 |
| 数量 | 1個 |
| カート合計 | $1,337.00 |
| ストアクレジット | $8.26 |

購入可能な残高よりも、商品価格が大幅に高い状態だった。

この段階では、`Place order` はクリックしていない。

### STEP 6：注文確定処理を省略してGETリクエストを送信

Burp SuiteのRepeaterを開き、STEP 4で保存した注文完了用リクエストを確認した。

```http
GET /cart/order-confirmation?order-confirmed=true HTTP/2
```

リクエストは変更せず、Repeaterから `Send` をクリックして送信した。

通常の購入フローに存在する `POST /cart/checkout` は、この高額商品に対して実行していない。

**確認結果**

サーバーから以下のレスポンスが返された。

```http
HTTP/2 200 OK
```

ただし、HTTPステータスが200であることだけでは、購入処理への影響を断定できない。

そのため、レスポンス内容とブラウザ上の状態を追加で確認した。

### STEP 7：RepeaterのRenderで結果を確認

Repeaterの `Response → Render` を開いた。

**確認結果**

ラボのステータスが `LAB Solved` に変化していた。

これにより、正規のcheckoutを省略した操作が、ラボの達成条件を満たしたことを確認した。

### STEP 8：ブラウザで状態の変化を確認

Burp専用ブラウザに戻り、カート画面を更新した。

**確認結果**

| 項目 | 結果 |
|---|---|
| ラボ | Solved |
| カート | 空になった |
| ストアクレジット | $8.26のまま |

通常の購入では$91.74が残高から差し引かれたが、今回の操作では革ジャンの代金が差し引かれていなかった。

さらに、カート内の商品が消え、ラボもSolvedになった。

**この結果から、正規の購入確定処理を省略して注文完了用リクエストを直接送信することで、購入制限を回避できることを確認した。**

## 4. 検証結果の比較

### 4.1 正常な購入フロー

```text
商品をカートに追加
    ↓
POST /cart/checkout
    ↓
303 See Other
    ↓
GET /cart/order-confirmation?order-confirmed=true
    ↓
200 OK
    ↓
注文完了画面
```

正常購入では、商品の購入代金がストアクレジットから差し引かれた。

### 4.2 今回の攻撃フロー

```text
革ジャンをカートに追加
    ↓
POST /cart/checkout を実行しない
    ↓
Repeaterから注文完了用GETを直接送信
    ↓
200 OK
    ↓
LAB Solved
    ↓
ブラウザ更新後、カートが空になる
    ↓
ストアクレジットは$8.26のまま
```

### 4.3 比較表

| 項目 | 正常購入 | 攻撃時 |
|---|---|---|
| 対象商品 | Hexbug Battleground Tarantula Double Pack | Lightweight l33t leather jacket |
| 商品価格 | $91.74 | $1,337.00 |
| `POST /cart/checkout` | 実行した | 実行していない |
| 注文完了用GET | 通常フローでアクセス | Repeaterから直接送信 |
| 残高変化 | $100.00 → $8.26 | $8.26のまま |
| カート | 通常購入を完了 | GET送信後に空になった |

### 4.4 実証できたこと

1. 正常な購入フローでは、checkout後に注文完了ページへのGETが発生していた。
2. 正常購入時には、商品の代金がストアクレジットから差し引かれた。
3. 高額商品をカートに追加したあと、checkoutを省略して注文完了用GETを送信できた。
4. Repeaterのレスポンスとして `200 OK` が返された。
5. ラボのステータスがSolvedになった。
6. ブラウザ上でカートが空になった。
7. ストアクレジットが減少していなかった。

## 5. 脆弱性の根本原因

### 5.1 購入フローの検証不足

今回の問題は、購入手順の途中に存在する必要な処理を省略しても、後続の注文完了処理へ進めてしまうことである。

Webアプリケーションでは、利用者が必ずしも画面に表示された順番どおりに操作するとは限らない。

URLを直接入力したり、Burp SuiteなどのツールからHTTPリクエストを再送信したりできる。

そのため、画面遷移の順番を前提にしただけの実装では、処理フローの制限を回避される可能性がある。

### 5.2 問題のある実装例

以下は問題の仕組みを説明する擬似コードであり、実際のラボのソースコードではない。

```javascript
app.get("/cart/order-confirmation", (req, res) => {
  completeOrder(req.session.cart);
  res.render("order-confirmation");
});
```

この例では、注文確定処理が完了したかを確認せず、注文完了処理を実行している。

このような実装では、正常な購入フローを経由せずに完了処理が実行される可能性がある。

### 5.3 HTTPメソッドだけの問題ではない

今回の注文完了用リクエストはGETメソッドだった。

一般にGETは情報取得を目的とするメソッドであり、注文の確定などの状態変更をGETへのアクセスだけで発生させる設計は避けるべきである。

ただし、今回の根本原因はGETメソッドを使用していることだけではない。

**サーバー側が注文の状態と処理順序を適切に検証できていないこと**が中心的な問題である。

GETをPOSTに変更するだけでは、処理フローの不備は解消できない。

## 6. 推奨対策

### 6.1 サーバー側で注文状態を管理する

注文処理には、サーバー側で管理する明確な状態を設ける。

例：

```text
Pending（未確定）
    ↓
Confirmed（購入確定）
    ↓
Completed（完了）
```

各状態への遷移には、業務上必要な条件を満たしていることを要求する。

これは対策の設計例であり、ラボで実際に使用されている状態名ではない。

### 6.2 注文確定処理の完了を検証する

注文完了処理を実行する前に、対象注文が正常に購入確定されているかをサーバー側で確認する。

必要な処理が未完了の場合は、後続の操作を拒否する。

### 6.3 残高の検証と減算を一貫して行う

ストアクレジットの検証と注文確定を、サーバー側で安全に処理する。

残高不足の状態で注文完了にならないよう、残高検証・代金減算・注文状態の更新を整合性のある処理として実装する。

実装上は、データベーストランザクションなどを用いた一貫性の確保も重要になる。

### 6.4 注文完了ページは確定済み注文の参照に限定する

注文完了ページを表示するためのリクエストによって、新しい注文が確定したり、決済条件が省略されたりしない設計にする。

完了画面の表示と、注文状態を変更する処理は適切に分離する。

### 6.5 処理順序の異常系テストを実施する

以下のような検証を実施する。

- カート追加後に注文完了URLへ直接アクセスする
- 注文確定を省略して後続処理を実行する
- 注文完了リクエストを再送信する
- 残高不足の状態で後続処理にアクセスする
- 過去の注文完了URLを再利用する
- 異なるアカウントから注文完了URLへアクセスする

これらは今後のテスト観点であり、今回すべてを実施したわけではない。

## 7. 想定される被害

### 7.1 今回実証した影響

- 正規の購入確定処理を省略できた
- 注文完了用のGETリクエストを直接実行できた
- ストアクレジット不足の状態でラボの購入条件を満たした
- 代金が減算されないままカートが空になった

### 7.2 実際のECサイトで想定される被害

同様の脆弱性が存在する場合、次のような被害が考えられる。

- 代金の支払いを伴わない不正な注文
- 残高不足による購入制限の回避
- 商品の不正取得
- 注文状態と決済状態の不整合
- 売上や利益の損失
- 注文・配送業務への影響

ただし、今回のラボでは実際の商品発送や内部の注文データベースまでは調査していない。

これらの被害は一般的な想定リスクであり、すべてを実証したわけではない。

## 8. 検証の限界と未確認事項

今回の検証では、以下は確認していない。

- サーバー内部の注文状態管理
- データベースに保存された注文レコード
- 商品発送処理の実行有無
- 実際の決済システムとの連携
- ほかの商品でも同様の操作が成立するか
- 別のアカウントでも同様の操作が成立するか
- 注文完了リクエストの繰り返し送信による影響
- 実際の企業システムでの再現性

したがって、今回断定できるのは、**正規のcheckoutを省略した操作でラボがSolvedとなり、カートが空になり、ストアクレジットが減算されなかったこと**までである。

内部の注文レコード生成や発送処理については未確認とする。

### 9.2 理解できたこと

- 正規の購入フローを省略する攻撃の仕組み
- HTTPリクエストの送信順序が業務処理に与える影響
- サーバー側で注文状態を管理する必要性
- HTTP 200 OKと業務処理の成功は同義ではないこと
- 複数の証拠から脆弱性の成立を判断する方法
- 実証事実と未検証の影響を区別する重要性

### 9.3 客観的な理解度評価

今回の選択式問題では5問すべてに自信ありと回答し、全問正解した。

処理フローの検証不足、サーバー側の対策、HTTPレスポンスの解釈、攻撃結果の判断について、今回の問題の範囲では理解を確認できた。

一方、ラボは公式Solutionに沿って進めたため、未知のシステムで同様の不備を独力で発見できるかは未評価である。

### 9.4 復習課題

1. 正常な購入時に発生するHTTP通信を、自分で整理できるようにする。
2. 注文状態の管理と処理順序の検証が必要な理由を説明する。
3. HTTP 200 OKと、注文完了の証拠を区別する。
4. 決済処理と注文状態の更新に必要な整合性を学ぶ。
5. 次のラボでは、公式Solutionを確認する前に処理順序を変えた検証仮説を考える。

## 10. 今回の学習成果

今回のラボでは、リクエスト本文の価格や数量を変更することなく、**HTTPリクエストを送信する順序を変更することで脆弱性を悪用できた**。

正常な購入フローを観察したことで、注文確定処理と注文完了処理が別のHTTPリクエストで構成されていることが分かった。

さらに、注文確定処理を省略して注文完了用GETを直接送信した結果、購入制限を回避できた。

この検証を通じて、**Webアプリケーションの脆弱性は入力値の検証不足だけでなく、処理の順序や状態管理の不備からも発生する**ことを学んだ。

今後は、単一のHTTPリクエストだけでなく、複数のリクエストによって構成される業務フロー全体にも注目して検証する。
