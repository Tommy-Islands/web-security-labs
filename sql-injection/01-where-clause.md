# SQL Injection：WHERE句の条件回避

## 攻撃シナリオと背景

### 想定するシステム

商品カテゴリによる絞り込み機能を備えたECサイトを想定する。

このサイトでは、商品情報に公開・非公開の状態が設定されており、通常の画面操作では公開済みの商品だけが表示される。

商品カテゴリを選択すると、URLパラメータ `category` を使用してサーバーに検索条件が送信される。

### 攻撃者の目的

攻撃者は、商品カテゴリの絞り込み機能に存在するSQLインジェクションの脆弱性を悪用し、アプリケーションが本来表示しない情報を取得することを狙う。

今回のシナリオでは、主に以下を目的とする。

- 非公開の商品情報を取得する
- 商品カテゴリによる検索条件を回避する
- 公開状態による表示制限を回避する

### 想定する攻撃の流れ

**第1段階：入力箇所の特定**

攻撃者は商品カテゴリの選択時に送信されるHTTPリクエストを確認する。

```http
GET /filter?category=Food+%26+Drink HTTP/2
```

`category` パラメータが検索条件に使用されていると推測し、検証対象とする。

**第2段階：SQLインジェクションの兆候を調査**

`category` の値にシングルクォート `'` を追加して送信する。

通常時はHTTP 200だったが、変更後はHTTP 500が返された。

この結果から、入力値がサーバー内部の処理に影響している可能性を確認した。

**第3段階：SQLコメントによる条件の変更**

入力値に `'--` を追加して送信したところ、HTTP 200に戻った。

SQLコメントによって後続のSQLが無効化され、構文エラーが解消された可能性があると判断した。

**第4段階：検索条件の回避**

以下の文字列を使用して、WHERE句の条件を変更する。

```sql
Food & Drink' OR 1=1--
```

`OR 1=1` によって検索条件を常に真にし、`--` によって後続の公開条件をコメントアウトする。

検証の結果、通常時よりも取得される商品数が増加し、PortSwiggerのラボがSolvedとなった。

### 想定される被害

**今回のラボで確認した影響**

- 本来のカテゴリによる絞り込みの回避
- 非公開の商品情報の取得

**実際のECサイトで想定されるビジネス上の影響**

- 発売前の商品名や価格など、未公開の商品情報の漏えい
- 販売戦略や新商品の情報が外部に知られることによる競争上の不利益
- 情報管理に対する顧客や取引先からの信用低下

また、SQLインジェクションの成立条件やデータベース権限によっては、さらに広い範囲の情報漏えいにつながる可能性がある。

ただし、今回の検証では別テーブルからの情報取得は実施していない。

### 今回の検証範囲と限界

今回実施した検証は、商品カテゴリを指定するGETリクエストの改ざんと、そのレスポンスの比較である。

HTTPステータスの変化、商品数の増加、ラボのSolved状態を確認した。

一方、サーバー内部のSQL実装やデータベースの権限設定は直接確認していない。

そのため、攻撃の内部処理については、SQLの一般的な動作とラボの検証結果に基づく考察として扱う。

## 1. 検証概要

**学習環境：** PortSwigger Web Security Academy  
**使用ツール：** Burp Suite Community Edition  
**対象機能：** 商品カテゴリの絞り込み機能  
**対象パラメータ：** `category`  
**結果：** Lab Solved

### 検証目的

商品カテゴリを指定するHTTPリクエストのパラメータを変更し、SQLインジェクションによって本来取得できない非公開商品を取得できるか検証する。

## 2. 検証手順と結果

### ① 正常なリクエスト

```http
GET /filter?category=Food+%26+Drink HTTP/2
```

結果：`200 OK`

通常の商品カテゴリの絞り込みが動作することを確認した。

### ② シングルクォートによる検証

```http
GET /filter?category=Food+%26+Drink' HTTP/2
```

結果：`500 Internal Server Error`

シングルクォートを追加するとサーバー内部エラーが発生した。

この結果から、入力値がSQL文の構文に影響している可能性を考えた。

### ③ SQLコメントによる検証

```http
GET /filter?category=Food+%26+Drink'-- HTTP/2
```

結果：`200 OK`

SQLコメントを追加すると正常なレスポンスに戻った。

### ④ 条件式の変更

```http
GET /filter?category=Food+%26+Drink'+OR+1=1-- HTTP/2
```

結果：`200 OK`

通常のカテゴリ表示と比較して商品数が増加した。

また、PortSwiggerのラボが `Solved` になったことを確認した。

## 3. 原因の考察

今回の脆弱性は、ユーザーから受け取ったカテゴリの値が、SQL文の構造を変更できる形で組み込まれているために発生すると考えられる。

`OR 1=1` によってWHERE句の条件を常に真にし、`--` によって後続のSQLをコメントアウトすることで、公開状態の絞り込みを回避できた。

※ SQL文の実装そのものは確認していないため、内部の処理についてはラボの仕様と検証結果に基づく考察である。

## 4. 想定される影響

- 非公開の商品情報が取得される
- 本来の検索条件による制限が回避される
- アプリケーションの実装によっては、ほかのデータへの不正アクセスにつながる可能性がある

## 5. 推奨対策

**プリペアドステートメント（パラメータ化クエリ）の利用**

ユーザー入力をSQL文の構造として解釈させず、データとして安全に扱う。

加えて、データベース接続アカウントの権限を必要最小限にする。

## 6. 学習したこと

今回の検証では、入力フォームが存在しなくても、HTTPリクエストのパラメータを変更することで脆弱性を検証できると学んだ。

Burp SuiteのHTTP historyで通信を確認し、Repeaterでリクエストを編集・再送信する基本操作を実践した。

今後は、SQLのWHERE句やコメント構文について理解を深め、ペイロードがSQL文にどのような影響を与えるか、自分で説明できるようにしたい。
