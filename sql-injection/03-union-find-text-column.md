# SQL Injection：UNION攻撃で文字列を取得できる列の特定

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | SQL injection UNION attack, finding a column containing text |
| 使用ツール | Burp Suite Community Edition |
| 検証対象 | ECサイトの商品カテゴリ絞り込み機能 |
| 対象パラメータ | `category` |
| 脆弱性の種類 | SQLインジェクション（UNION攻撃） |
| 検証結果 | Solved |

### 検証目的

SQLインジェクションのUNION攻撃を利用し、元のSELECT文が返す列数を特定したうえで、文字列を格納でき、HTTPレスポンスに出力できる列を調査する。

前回のラボではUNION攻撃に必要な列数を特定した。

今回は、そこから一歩進み、指定した文字列を検索結果に出力できるか確認する。

## 2. 攻撃シナリオと背景

### 想定するシステム

商品カテゴリによる絞り込み機能を備えたECサイトを想定する。

このECサイトでは、商品情報をデータベースで管理しており、利用者はカテゴリを選択することで該当する商品を検索できる。

検索処理では、HTTPリクエストの `category` パラメータが使用される。

### 攻撃者の目的

攻撃者は、商品検索機能に存在するSQLインジェクションを悪用し、本来アクセスできないデータベース内の情報を取得することを狙う。

想定される標的には、会員情報、注文情報、認証関連データなどがある。

ただし、それらの情報が実際のラボ環境に存在するかは確認していない。

### 想定する攻撃の流れ

**第1段階：SQLインジェクションの成立確認**

カテゴリ検索パラメータの入力値を変更し、SQLの処理に影響を与えられるか調査する。

**第2段階：UNIONに必要な列数の特定**

`UNION SELECT NULL` の列数を増やし、正常なレスポンスが得られる列数を調べる。

**第3段階：文字列を格納できる列の特定**

列数を固定し、各列に文字列を入れて、データ型の互換性を調査する。

**第4段階：検索結果への出力確認**

指定した文字列が、商品一覧のHTMLに表示されるか確認する。

**第5段階：別テーブルからの情報取得（未実施）**

必要な列数、データ型、表示位置が分かれば、データベースの権限や構造などの条件次第で、別テーブルの情報取得につながる可能性がある。

### 今回の検証範囲

今回実施したのは、第2段階から第4段階までである。

指定した文字列の検索結果への出力は確認したが、個人情報などの実データを別テーブルから取得する検証は実施していない。

## 3. 検証環境

- OS：Parrot Security（VirtualBox上の仮想環境）
- 使用ツール：Burp Suite Community Edition
- 対象：PortSwigger Web Security Academyの学習用ラボ
- 使用機能：Proxy / HTTP history / Repeater

## 4. 検証手順と結果

### 4.1 正常なリクエストの確認

商品カテゴリを選択した際のGETリクエストをBurp SuiteのHTTP historyから取得した。

Repeaterに送信し、変更前の正常なレスポンスを確認した。

**結果：HTTP 200 OK**

以降の検証では、`category` パラメータにSQLを追加して挙動の違いを調査した。

### 4.2 UNION攻撃に必要な列数の特定

まず、NULLの数を1つずつ増やし、UNIONで結合できる列数を調べた。

**1列での検証**

```sql
Gifts' UNION SELECT NULL--
```

結果：HTTP 500 Internal Server Error

**2列での検証**

```sql
Gifts' UNION SELECT NULL,NULL--
```

結果：HTTP 500 Internal Server Error

**3列での検証**

```sql
Gifts' UNION SELECT NULL,NULL,NULL--
```

結果：HTTP 200 OK

#### 結果一覧

| 検証内容 | 列数 | HTTPステータス |
|---|---|---|
| `UNION SELECT NULL` | 1 | 500 |
| `UNION SELECT NULL,NULL` | 2 | 500 |
| `UNION SELECT NULL,NULL,NULL` | 3 | 200 |

3列を指定した場合に正常なレスポンスが得られた。

この結果から、元のSELECT文が3列のデータを返していると判断した。

ただし、HTTP 500だけでは列数不一致を断定できないため、正常応答との比較に基づく判断である。

### 4.3 文字列を格納できる列の特定

列数を3列に固定し、NULLのうち1つを文字列 `'test'` に置き換えて検証した。

**1列目の検証**

```sql
Gifts' UNION SELECT 'test',NULL,NULL--
```

結果：HTTP 500 Internal Server Error

**2列目の検証**

```sql
Gifts' UNION SELECT NULL,'test',NULL--
```

結果：HTTP 200 OK

#### 結果一覧

| 検証対象 | ペイロード | 結果 |
|---|---|---|
| 1列目 | `UNION SELECT 'test',NULL,NULL` | 500 |
| 2列目 | `UNION SELECT NULL,'test',NULL` | 200 |
| 3列目 | 未検証 | 不明 |

2列目に文字列を配置した場合に正常なレスポンスが得られた。

このことから、2列目は文字列を受け付けると判断した。

一方、1列目の500エラーについては、データ型の不一致が原因である可能性があるが、サーバー内部のエラー詳細までは確認していない。

### 4.4 HTTPレスポンスへの出力確認

2列目に `'test'` を指定して200 OKとなったため、Response内で `test` を検索した。

最初に、検索条件が見出しとして表示されている箇所を確認した。

```html
<h1>Gifts&apos; UNION SELECT NULL,&apos;test&apos;,NULL--</h1>
```

この表示だけでは、入力値がそのままHTMLへ反映されている可能性があるため、UNION攻撃の成功を判断する証拠としては不十分である。

さらに調査したところ、商品一覧のHTML内に以下を確認した。

```html
<table class="is-table-numbers">
    <tbody>
        <tr>
            <th>test</th>
        </tr>
    </tbody>
</table>
```

商品一覧の結果部分に `test` が出力されていることから、UNION SELECTで指定した文字列が検索結果へ追加されたと判断した。

### 4.5 ラボ指定文字列での最終検証

ラボから指定された文字列 `hGATrK` を、文字列を受け付ける2列目に指定した。

```sql
Gifts' UNION SELECT NULL,'hGATrK',NULL--
```

**結果：Lab Solved**

以上により、今回のラボのクリア条件を満たした。

## 5. 技術的な原因と考察

### 5.1 UNION攻撃の仕組み

UNIONは、複数のSELECT文の結果を結合するSQLの機能である。

例えば、次のSQLを考える。

```sql
SELECT id, name, price
FROM products
WHERE category = 'Gifts'
UNION
SELECT NULL, 'test', NULL;
```

※ このSQLは理解のための仮想例であり、ラボ内部の実際のSQL文を確認したものではない。

元のSELECTが3列である場合、追加するSELECTも3列にする必要がある。

また、対応する列のデータ型には互換性が求められる。

### 5.2 NULLを使用する理由

NULLは値が不明、または存在しないことを表すSQLの特殊な値である。

多くのデータ型と互換性があるため、UNIONで列数を調査する際に利用しやすい。

### 5.3 文字列の出力位置を特定する理由

UNIONで列数が一致しても、任意の列に文字列を格納できるとは限らない。

例えば、元のSELECTが整数型、文字列型、整数型の順に結果を返す場合、追加するSELECTも対応する位置のデータ型を考慮する必要がある。

また、文字列を受け付ける列であっても、その値がHTTPレスポンスに出力されるとは限らない。

そのため、データ型の互換性と出力位置をそれぞれ確認する必要がある。

### 5.4 根本原因

SQLインジェクションは、ユーザー入力がSQL文の構造を変更できる形で処理されることで成立する。

以下は脆弱な実装の概念例である。

```javascript
const sql =
  "SELECT id, name, price FROM products WHERE category = '" +
  category +
  "'";
```

入力値をSQL文字列へ直接連結すると、本来データとして扱うべき文字列がSQLの一部として解釈される可能性がある。

今回のラボでは、このような問題によりUNION SELECTを追加できる状態だったと考えられる。

ただし、サーバー側の実際のソースコードは確認していない。

## 6. 想定される被害とリスク

### 今回実証した影響

- UNION SELECTによる検索結果の追加
- 文字列を受け付ける列の特定
- 指定した文字列のHTTPレスポンスへの出力

### 実際のシステムで想定される影響

データベースの構造や権限によっては、以下の被害につながる可能性がある。

- 会員情報などの個人情報の漏えい
- 注文履歴などの業務情報の漏えい
- 認証関連情報や内部管理情報への不正アクセス
- 企業の信用低下や情報漏えい対応に伴う事業上の損失

### リスク評価上の注意点

今回の検証では、別テーブルの構造、データベースユーザーの権限、個人情報の取得可否は確認していない。

そのため、機密情報の漏えいが実際に可能であると断定することはできない。

## 7. 推奨対策

### 7.1 プリペアドステートメントの使用

最優先の対策は、SQL文の構造とユーザー入力値を分離することである。

```javascript
// パラメータ化クエリの概念例
const sql =
  "SELECT id, name, price FROM products WHERE category = ?";

db.execute(sql, [category]);
```

この方式では、ユーザー入力をSQL命令として解釈させず、値として扱う。

※ 実際のプレースホルダー構文や実行方法は、データベースとライブラリにより異なる。

### 7.2 データベース権限の最小化

アプリケーションが使用するデータベースアカウントには、必要なテーブルに対する必要最小限の権限のみを付与する。

### 7.3 エラー情報の適切な管理

利用者に詳細なSQLエラーを公開しない。

ただし、エラー表示を隠すことだけではSQLインジェクションの根本的な解決にはならない。

### 7.4 WAFによる多層防御

WAFによる不審な通信の検知・遮断も有効な補助策となる。

ただし、アプリケーション側の安全なSQL実装の代わりにはならない。

## 8. 学習内容と振り返り

今回のラボを通して、以下を学んだ。

- UNION攻撃ではSELECT文の列数を一致させる必要がある
- 対応する列のデータ型にも互換性が必要になる
- NULLを使うことで列数を調査しやすくなる
- 文字列を受け付ける列と、画面に表示される列は区別して考える必要がある
- HTTP 200だけでは攻撃成功の十分な証拠にならない
- 検索条件がHTMLに表示されたことと、SQLの検索結果に追加されたことは異なる
- 脆弱性の根本対策はSQL構造と入力値を分離することである
