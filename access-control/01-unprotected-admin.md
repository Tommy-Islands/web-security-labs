# Broken Access Control：保護されていない管理者機能の検証

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Unprotected admin functionality |
| 難易度 | Apprentice |
| 脆弱性の種類 | Broken Access Control（アクセス制御の不備） |
| 検証対象 | 管理者画面・ユーザー削除機能 |
| 検証環境 | Parrot Security（VirtualBox） |
| 使用ツール | Burp Suite Community Edition / ブラウザ |
| 検証結果 | Solved |

### 検証目的

管理者としてログインしていない状態で、管理者専用ページへのアクセスや管理者機能の実行が可能かを確認する。

また、`robots.txt` によるURLの発見と、サーバー側の認可不備の違いを理解する。

## 2. 攻撃シナリオと背景

### 2.1 想定するシステム

一般利用者向けのWebサイトに、ユーザー管理機能を備えた管理者画面が存在すると想定する。

管理者はユーザー一覧を確認し、必要に応じてアカウントを削除できる。

これらの管理機能は、本来、適切な管理者権限を持つ利用者だけが実行できる必要がある。

### 2.2 攻撃者の目的

攻撃者は、管理者権限を持たない状態で管理者機能にアクセスし、ユーザーアカウントの削除など、本来許可されていない操作を実行することを狙う。

### 2.3 想定する攻撃の流れ

**第1段階：公開画面の調査**

一般ユーザー向けの画面を確認し、管理者機能へのリンクが表示されているかを調査する。

**第2段階：管理者画面のURLを発見**

公開されている `robots.txt` などから、管理者画面につながるパスを調査する。

**第3段階：管理者画面へのアクセス**

発見したURLへ直接アクセスし、認証・認可によるアクセス制限が行われるか確認する。

**第4段階：管理者機能の実行**

権限のない利用者でも、管理者専用の操作を実行できるか検証する。

今回のラボでは、指定ユーザーの削除機能を検証対象とした。

## 3. 検証手順と結果

### 3.1 トップページの調査

最初に、ラボのトップページを確認した。

**確認結果**

ナビゲーションには次の項目のみが表示されていた。

```text
Home | My account
```

管理者専用ページへのリンクは確認できなかった。

ただし、画面にリンクが存在しないことは、サーバー側で管理者機能へのアクセスが制限されていることを意味しない。

### 3.2 robots.txtの確認

次に、以下のパスへアクセスした。

```http
GET /robots.txt
```

**確認したレスポンス本文**

```text
User-agent: *
Disallow: /administrator-panel
```

この記述から、`/administrator-panel` というパスの存在を確認した。

`User-agent: *` はすべてのクローラーを対象とする指定である。

`Disallow: /administrator-panel` は、そのパスの巡回を控えるようクローラーへ伝えるものであり、一般利用者によるアクセスを禁止する機能ではない。

### 3.3 管理者画面への直接アクセス

`robots.txt` で発見したパスに直接アクセスした。

```http
GET /administrator-panel
```

**結果**

- 管理者画面が表示された
- ユーザー一覧を閲覧できた
- ユーザー削除用のDeleteボタンが表示された

管理者としてログインしていない状態でも、管理者向け画面にアクセスできることを確認した。

この段階では、管理操作そのものが実行可能かはまだ確認していない。

### 3.4 ユーザー削除機能の検証

管理者画面のユーザー一覧から、ラボの指定対象である `carlos` を確認した。

対象ユーザーのDeleteボタンをクリックし、削除処理を実行した。

**結果**

PortSwiggerのラボがSolvedになった。

この結果から、管理者権限がない状態でも、管理者専用のユーザー削除機能を実行できることを確認した。

なお、削除時のHTTPメソッド、リクエストパス、ステータスコードなどの詳細は記録していないため、推測による記載は行わない。

### 3.5 検証結果一覧

| 検証項目 | 結果 |
|---|---|
| 一般画面の確認 | Home・My accountのみ |
| `robots.txt` の確認 | `/administrator-panel` を発見 |
| 管理者画面への直接アクセス | 成功 |
| ユーザー一覧の閲覧 | 成功 |
| Deleteボタンの表示 | 確認 |
| `carlos` の削除 | 成功・Solved |

## 4. 技術的な原因と考察

### 4.1 認証と認可の違い

**認証（Authentication）**

アクセスしている利用者が誰なのかを確認する処理。

例：IDとパスワードによるログイン。

**認可（Authorization）**

その利用者に、特定の情報へのアクセスや操作を行う権限があるか確認する処理。

例：管理者だけがユーザーを削除できるよう制限する。

今回のラボで問題になったのは、主に認可の不備である。

### 4.2 robots.txtはアクセス制御ではない

`robots.txt` はクローラー向けの巡回ルールを指定するためのファイルである。

そのため、次のように管理者画面を指定しても、

```text
Disallow: /administrator-panel
```

一般利用者からのアクセスを拒否する効果はない。

むしろ、公開されたファイルから管理者画面のURLを推測する手がかりとなる場合がある。

ただし、今回の脆弱性の根本原因はURLが記載されていたことではない。

管理者権限を確認せず、管理者機能へのアクセスと操作を許可していたことが問題である。

### 4.3 URLを隠すことと権限を制限することの違い

管理者向けのリンクやボタンを非表示にしても、サーバー側で操作権限を検証していなければ、URLへの直接アクセスやHTTPリクエストの送信によって操作できる可能性がある。

そのため、画面側の表示制御だけに依存してはならない。

### 4.4 根本原因

管理者画面とユーザー削除機能に対する、サーバー側の認可チェックが欠落、または不適切であったと考えられる。

なお、サーバー側のソースコードは確認していないため、具体的な実装上の欠陥までは特定していない。

## 5. 想定される被害とリスク

### 5.1 今回実証した影響

- 管理者権限を持たない状態での管理者画面へのアクセス
- ユーザー一覧の閲覧
- 指定ユーザーの削除

### 5.2 実際のシステムで想定される影響

同様の脆弱性が実際のWebサービスに存在した場合、次のような被害につながる可能性がある。

- 顧客アカウントの不正削除
- 利用者がサービスを利用できなくなる
- 業務の停止や運用上の障害
- 権限のない利用者による管理情報の閲覧
- 情報管理上の信用低下

### 5.3 検証範囲と限界

今回の検証では、ラボで指定された `carlos` の削除まで確認した。

一方、以下については未検証である。

- データベース全体へのアクセス
- ほかの管理者機能の実行可否
- 管理者権限への昇格
- 実際の企業システムにおける同様の問題の存在

これらの影響が実際に成立することまでは断定しない。

## 6. 推奨対策

### 6.1 サーバー側での認可チェック

管理者専用機能を実行する前に、サーバー側で利用者の権限を確認する。

以下は処理の考え方を表す擬似コードである。

```javascript
if (!user.isAuthenticated) {
  return 401;
}

if (user.role !== 'admin') {
  return 403;
}

deleteUser(targetUserId);
```

認証されていない利用者や管理者権限のない利用者に対して、削除操作を許可しない。

実際には、セッションの検証、権限情報の信頼性、アクセス対象なども適切に確認する必要がある。

### 6.2 管理者画面と操作用エンドポイントの保護

管理者画面の表示だけでなく、ユーザー削除などの操作を処理するエンドポイントに対しても、認可チェックを実装する。

また、管理画面の各機能に必要な権限を明確に定義する。

### 6.3 最小権限の原則

利用者には、業務上必要な最小限の権限のみを付与する。

一般ユーザーに管理者操作を許可しない。

### 6.4 デフォルトで拒否する設計

明示的に許可されていないアクセスは、原則として拒否する。

画面ごと・操作ごとに適切なアクセス制御を適用する。

### 6.5 権限別のテスト

未認証ユーザー、一般ユーザー、管理者など、権限の異なる利用者で管理機能を検証する。

URLへの直接アクセスだけでなく、操作用のHTTPリクエストについても確認する。

### 6.6 robots.txtへの依存を避ける

`robots.txt` を認証・認可の代替として使用しない。

また、公開ファイルに不要な内部パス情報を記載しないよう注意する。

## 7. 学習内容と振り返り

### 7.1 今回学んだこと

- 認証と認可は別の仕組みである
- 管理者用リンクが表示されないことはアクセス制御の証拠にならない
- `robots.txt` はアクセス制御機能ではない
- 管理者画面へアクセスできることと、管理操作を実行できることは分けて検証する
- サーバー側で権限を確認する必要がある
- 権限のない利用者でも管理機能を実行できる場合、重大な被害につながる可能性がある
- 検証で確認した事実と、想定される被害を区別して報告する

### 7.2 理解度チェック

全5問中5問正解。

認証と認可、サーバー側の権限確認、`robots.txt` の役割、検証範囲の考え方について、基礎知識を確認できた。

### 7.3 今後の課題

- Burp Suiteでアクセス制御に関するHTTPリクエストを確認する
- 未認証・一般ユーザー・管理者の権限の違いを検証する
- 垂直方向の権限昇格と水平方向のアクセス制御不備を理解する
- IDOR（Insecure Direct Object Reference）について学ぶ
- 検証証拠としてHTTPリクエスト・レスポンスを記録できるようになる
