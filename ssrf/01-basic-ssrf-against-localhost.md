# SSRF：localhost経由の内部管理画面アクセスとユーザー削除

## 1. 検証概要

| 項目 | 内容 |
|---|---|
| 学習プラットフォーム | PortSwigger Web Security Academy |
| ラボ名 | Basic SSRF against the local server |
| 難易度 | Apprentice |
| 分野 | Server-Side Request Forgery（SSRF） |
| 対象機能 | 商品在庫確認（POST /product/stock） |
| 使用ツール | Burp Suite Community Edition（Proxy / HTTP history、Repeater） |
| 検証結果 | LAB Solved |
| 理解度チェック | 4/5問正解（80%） |

### 検証目的

商品在庫確認APIに渡す外部URLを変更し、Webサーバーから内部の管理画面へアクセスできるかを検証する。内部管理機能に対するリクエストが実行されることを確認し、SSRFの発生条件、影響、対策を整理する。

---

## 2. 実務上の攻撃シナリオ

### 2.1 想定するシステム

ECサイトが商品在庫を確認する際に、別サービスの在庫APIへサーバー側からHTTPリクエストを送る構成を想定する。一般利用者は在庫確認機能を使えるが、管理用のユーザー削除機能は内部ネットワークからのみ利用可能とする。

### 2.2 攻撃者と目的

攻撃者は通常の商品ページを閲覧できる外部利用者。商品在庫を確認するリクエストに宛先URLを指定する項目があると気づき、本来は接続できない内部管理画面へサーバー経由でアクセスすることを狙う。

### 2.3 攻撃から被害までの流れ

1. 攻撃者は在庫確認時の通信を観察し、\`stockApi\`というURL指定用のパラメータを発見する。
2. 正規の在庫確認先を\`http://localhost/admin\`へ変更する。
3. サーバーが渡されたURLを検証せずに取得すると、サーバー自身から内部の管理画面へリクエストが送信される。
4. 管理画面のレスポンスからユーザー削除用の内部URLを把握する。
5. 今度は\`stockApi\`で内部の削除URLを指定し、管理機能にリクエストを送信させる。
6. 管理機能が内部からのアクセスを過度に信用する等の問題を抱えていれば、権限のないユーザー削除が行われる可能性がある。

### 2.4 想定被害・根本原因・対策の関係

**想定される被害：** 他人のアカウントの不正削除、業務アカウントの利用不能、管理操作の悪用、復旧・調査対応の負担。さらに内部ネットワーク上の他サービスに到達できる構成であれば、情報取得や追加操作につながるおそれもある。

**SSRFの根本原因：** サーバーがクライアント指定のURLを信用してリクエストし、\`localhost\`や内部アドレスへのアクセスを適切に制限していないこと。

**被害を成立させた追加条件：** 内部管理機能側で、その操作を実行する主体の認証・認可や外部からの間接アクセスに対する防御が不十分だったことが考えられる。サーバー内部の実装までは未確認。

**防止：** 在庫確認先を必要なサービスに限定し、URLと名前解決後の接続先を検証してループバック・内部宛の通信を遮断する。内部管理機能にも適切な認証・認可を設ける。

**検知：** 在庫確認処理から\`localhost\`、プライベートIP、管理用パス等への接続試行が発生していないか監視する。ユーザー削除など管理操作の監査ログと突き合わせて調査する。

**この節の企業被害は実務上の想定であり、今回の学習ラボで実際に発生した企業インシデントではない。**

## 3. 技術的背景

### 3.1 SSRFとは

Server-Side Request Forgery（SSRF）は、攻撃者が指定したURL等を使い、**アプリケーションのサーバーに意図しない宛先へのリクエストを送らせる**問題である。

利用者のブラウザから内部サービスへ直接アクセスできなくても、サーバーに代わりにアクセスさせられる場合がある。

### 3.2 localhostの意味

\`localhost\`は、リクエストを実行するコンピューター自身を指す。今回の\`stockApi\`はWebサーバー側が処理するため、\`http://localhost/admin\`の\`localhost\`は**利用者のPCではなく、リクエストを送るサーバー側の実行環境**を指す。

\`localhost\`と入力するだけで管理者権限が付与されるわけではない。サーバーが内部管理画面にアクセスでき、かつ管理機能側の制御が不十分なことが問題である。

### 3.3 URLを受け取る在庫確認機能

今回の商品在庫確認は、\`POST /product/stock\`の本文に\`stockApi\`というパラメータでURLを渡す形式だった。この入力値を書き換えることにより、サーバー側の通信先を変更できた。

## 4. 検証手順とHTTP通信

### STEP 1：商品在庫確認のリクエストを発見

商品ページで\`Check stock\`を実行し、Burp SuiteのHTTP historyから次のリクエストを確認してRepeaterへ送った。

\`\`\`http
POST /product/stock HTTP/2
Content-Type: application/x-www-form-urlencoded

stockApi=http%3A%2F%2Fstock.weliketoshop.net%3A8080%2Fproduct%2Fstock%2Fcheck%3FproductId%3D17%26storeId%3D1
\`\`\`

※ 要点を抜粋した通信例。実際のリクエストに含まれるセッションCookie等は公開しない。

この時点の\`stockApi\`は在庫確認サービスのURLを指していた。

### STEP 2：サーバー自身の管理画面へアクセス

Repeaterで\`stockApi\`の値を次のように変更し、送信した。

\`\`\`text
stockApi=http://localhost/admin
\`\`\`

レスポンス：

\`\`\`http
HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
\`\`\`

返されたHTML内に以下の要素が存在した。

\`\`\`html
<h1>Users</h1>
<div>
  <span>wiener - </span>
  <a href="/admin/delete?username=wiener">Delete</a>
</div>
<div>
  <span>carlos - </span>
  <a href="/admin/delete?username=carlos">Delete</a>
</div>
\`\`\`

一般利用者から通常の経路で表示されない内部管理画面のHTMLが取得され、\`carlos\`の削除リンクを確認できた。

### STEP 3：内部のユーザー削除URLを指定

同じリクエスト本文を以下に変更した。

\`\`\`text
stockApi=http://localhost/admin/delete?username=carlos
\`\`\`

送信後のレスポンス：

\`\`\`http
HTTP/2 302 Found
Location: /admin
Content-Length: 0
\`\`\`

削除用の内部URLに対する処理後、\`/admin\`へのリダイレクトが返された。

### STEP 4：ラボ達成を確認

ブラウザで**LAB Solved**を確認した。

\`302 Found\`のみでデータベース上の削除を完全に証明できるわけではないが、今回の学習環境ではこの操作によりラボの達成条件を満たした。

## 6. 根本原因と技術的考察

### 6.1 外部入力に基づく任意宛先へのアクセス

在庫確認用APIが受け取った\`stockApi\`を使ってHTTP通信を行う際、接続先を適切に検証していないと、在庫API以外のURLへアクセスできてしまう。

このラボでは\`localhost\`の管理画面に到達できた。

### 6.2 内部ネットワークを信用しすぎる危険性

「外部から管理画面に直接アクセスできない」ことだけに依存すると、SSRFのような内部からの間接アクセスで保護が回避されるおそれがある。

内部管理機能にも、**操作主体の認証・認可**を設ける必要がある。

### 6.3 脆弱な実装のイメージ

以下は概念説明のためのコードであり、ラボの実際の内部コードではない。

\`\`\`javascript
app.post("/product/stock", async (req, res) => {
  const response = await fetch(req.body.stockApi);
  res.send(await response.text());
});
\`\`\`

利用者指定の任意URLを検証せずに\`fetch\`へ渡すと、サーバーのアクセス権限を悪用される可能性がある。

- 他ユーザーのアカウントの不正削除・業務停止

- 構成次第での内部サービスの探索や情報漏えい

いずれも同種の問題が実環境で存在した場合の想定であり、今回のラボで確認した被害ではない。

## 8. 推奨対策と検知策

### 8.1 宛先URLの許可リスト

在庫取得で通信する必要のあるホスト・プロトコル・ポートだけを許可する。任意のURLを入力させず、可能であればサーバー側で固定の在庫サービスを利用する。

### 8.2 内部アドレスへのアクセス制限

\`localhost\`、ループバックアドレス、プライベートIP、リンクローカルアドレスなどへの不必要な接続を拒否する。

ホスト名を検証するときはDNS解決後の接続先も確認し、リダイレクトや名前解決結果の変化による回避も考慮する。ネットワーク側の送信先制限を併用する。

### 8.3 内部管理機能の認証・認可

内部からアクセスしても管理操作を無条件に許可せず、適切な認証と権限チェックを実施する。削除などの重要な処理は、実行主体と対象を監査できるようにする。

### 8.4 ログと異常検知

- 在庫確認処理の外部入力URLと接続先（機密情報を除く）
- \`localhost\`や社内IPへの不審な接続試行
- \`/admin\`など管理パスへの要求
- 管理操作の実行者・対象・日時・成否
- 在庫確認APIを利用した短時間の大量試行

これらを監視し、異常時はネットワーク接続ログと管理機能の監査ログを照合する。

### 8.5 検証ケース

| ケース | 期待動作 |
|---|---|
| 正規の在庫サービスURL | 必要な処理だけを許可 |
| localhost・ループバックへの接続 | 拒否 |
| プライベートIPへの不要な接続 | 拒否 |
| 許可先から内部URLへのリダイレクト | 不正な接続先なら拒否 |
| 内部管理APIを未認可ユーザーが操作 | 拒否 |

## 9. 検証の限界と未確認事項

- サーバーの内部構成や実際のIPアドレス
- 管理機能の内部認証・認可実装
- 削除後のデータベース状態
- localhost以外の宛先、ほかの内部サービスへの到達可否
- 実在する企業システムでの再現性と被害
- 最初の\`/admin\`への直接アクセスが具体的にどのレスポンスで拒否されたか（記録なし）

**確認済みのHTTPレスポンス、管理画面HTML、Solvedという事実を超えて断定しない。**

### 復習すべき点

**Q2：localhostの意味**

\`localhost\`は常に「自分のPC」という意味ではない。そのリクエストを実行している環境自身を指す。今回はWebサーバーが\`stockApi\`のURLにアクセスしていたため、Webサーバー側のlocalhostへアクセスした。

### 定着に向けた課題

1. 自分のPCが送信する通信と、Webサーバーが代理で送る通信の違いを区別する。
2. GET/POSTと、URLで指定するサーバー側のアクセス先を見分ける。
3. SSRFの宛先制限と、内部管理機能自体の認証・認可を別々の対策として理解する。

## 11. 今回の学習成果

商品在庫確認のリクエストに含まれる\`stockApi\`を書き換え、Webサーバーからlocalhostの管理画面へアクセスさせた。管理画面に表示された\`carlos\`の削除URLを指定し、\`302 Found\`とLAB Solvedを確認した。

特に重要なのは、**自分のPCからlocalhostへアクセスしたのではなく、Webサーバーにサーバー自身のlocalhostへアクセスさせた**という点である。

現段階では公式Solutionの再現とHTTP通信・レスポンスの観察を優先し、反復を通じて動作の理解を深めていく。
