## 2. 実務上の攻撃シナリオ

### 2.1 想定するシステムと攻撃者

ECサイトに商品の店舗別在庫を調べる`Check stock`機能がある。利用者は商品詳細画面からLondon、Paris、Milanなどの店舗を選択できる。

外部の利用者は通常の在庫照会を行えるが、サーバーでOSコマンドを任意に実行する権限は与えられていない。

### 2.2 攻撃から被害までの流れ

1. 攻撃者が在庫照会のHTTPリクエストを観察し、`storeId`が店舗指定に使われていることを確認する。
2. サーバー側が入力値をシェルコマンドの一部として組み立てている場合、店舗IDの後ろにシェルの特殊文字と別のコマンドを追加する。
3. シェルが入力をデータではなくコマンド構文として解釈すると、想定外のOSコマンドが実行される。
4. 出力がHTTPレスポンスへ返る構成であれば、攻撃者は実行結果を確認できる。
5. 実務では、実行ユーザーの権限次第で情報の窃取・ファイル改ざん・削除・サービス停止などの被害につながるおそれがある。

### 2.3 実証と想定被害の区別

| 観点 | 内容 |
|---|---|
| 今回実証したこと | `storeId`への`|whoami`追加でOSコマンドの実行結果と思われるユーザー名が返った |
| 今回観測した出力 | `peter-ea3ltU` |
| 実務上の想定被害 | 情報漏えい、データ改ざん・削除、権限次第でのサーバー侵害 |
| 根本原因 | 外部入力を適切に分離せずシェルコマンドの構文として解釈させていること |
| 防止策 | OSコマンド呼び出しの回避、安全なAPI・引数指定、許可リスト、最小権限 |
| 検知策 | 特殊文字を含むパラメータ、予期しないコマンド起動、異常な在庫照会の監視 |

**今回は`whoami`以外のOSコマンドを実行した事実はなく、ファイル改ざん等の被害は想定である。**

## 3. 技術的背景

### 3.1 OS Command Injectionとは

OS Command Injectionは、サーバー上でOSコマンドを実行する処理に外部入力が危険な形で組み込まれ、利用者が意図しないコマンドを実行できてしまう脆弱性である。

安全な実装では、外部入力はコマンド構文ではなくデータとして扱う必要がある。

### 3.2 パイプ記号`|`の意味

Unix系シェルで`|`は、**左側のコマンドの標準出力を右側のコマンドの標準入力へ接続する**パイプラインを表す。

今回の`|whoami`は、左側の処理の後ろに別のコマンド実行を組み込むために使われた。`whoami`自体は標準入力を必要としないが、パイプラインの右側のコマンドとして実行される。

### 3.3 URLエンコードと実行の関係

今回入力した`|whoami`は、HTTP本文の送信値として`%7cwhoami`の形にURLエンコードされていた。

`%7c`はパイプ記号`|`を表すエンコードであり、**URLエンコード自体がOSコマンドを実行するわけではない**。サーバーが受信データを復号後、シェルのコマンド文字列へ安全に分離せず組み込むことが問題となる。

### 3.4 Path Traversalとの違い

Path Traversalは主に想定外のファイル参照を引き起こす。一方、OS Command InjectionはOSコマンドを実行できるため、実行権限や実装次第で読み取りだけでなく変更・削除等にも影響が及ぶ。

ただし、どちらが常に深刻かは対象環境・取得できる権限・アクセスできる情報によって異なり、OS Command Injectionが必ず管理者権限を得られるわけではない。

## 4. 検証手順

### STEP 1：通常の在庫確認を実行

商品詳細ページから`Check stock`を開き、店舗（London / Paris / Milan）を選んで在庫照会を一度実行した。

### STEP 2：Burpで対象リクエストを確認

Burp Suiteで`POST /product/stock`を確認。本文には`productId`と`storeId`の2パラメータが含まれていた。

### STEP 3：Repeaterでパラメータを変更

リクエストをRepeaterへ送り、`storeId`の元の値に`|whoami`を追加した。

HTTP本文での追加部分は`%7cwhoami`となった。

### STEP 4：リクエストを再送信

改変後のリクエストをRepeaterから送信した。

### STEP 5：実行結果を確認

レスポンスには通常の在庫数の代わりに、`whoami`コマンドの出力であると判断できるユーザー名`peter-ea3ltU`が返った。

**LAB Solvedを確認した。**

## 5. 実証HTTP（再構成例）

**重要：以下は共有されたパラメータ・操作・観測結果をもとに再構成した説明用のHTTP例である。Burpの生のリクエスト・レスポンス全文は提供されていない。** 未提供の`productId`と`storeId`の元の値は伏せ字にしている。

### 5.1 改変したリクエストの説明例

```http
POST /product/stock HTTP/1.1
Host: <lab-id>.web-security-academy.net
Content-Type: application/x-www-form-urlencoded

productId=<product-id>&storeId=<original-store-id>%7cwhoami
```

- `<lab-id>`はドメインの匿名化。
- `<product-id>`と`<original-store-id>`は未提供の値のプレースホルダーであり、**実際に送信した文字列ではない**。
- `%7cwhoami`は実際に追加した攻撃文字列。
- `HTTP/1.1`や上記のヘッダーは説明用の形式で、実際の通信バージョン・ヘッダー構成を再現したものではない。

### 5.2 レスポンスの一部

**実際に報告されたレスポンス本文の出力：**

```text
peter-ea3ltU
```

在庫数ではなくOSコマンドの実行結果が返り、LAB Solvedとなった。

HTTPステータスコード、完全なレスポンスヘッダー、`Content-Type`、前後の本文、元の在庫数は未提供のため記載しない。上記はHTTPレスポンス全文の転載ではなく、確認された出力の抜粋である。

| 検証項目 | 実際に確認した結果 |

## 7. 推奨防止策と検知策

### 7.1 OSコマンド呼び出しを避ける

在庫照会などのアプリケーション処理にOSコマンドを使う必要がない場合は、DBアクセスや言語の標準ライブラリ等の安全なAPIを利用し、シェル呼び出しをなくす。

### 7.2 シェルを介さず引数を分離する

どうしても外部プログラムを起動する場合は、コマンド文字列をシェルに解釈させず、コマンド名と引数を別々に渡せる安全な実行APIを使用する。

シェル特殊文字の置換やエスケープだけに依存しない。

### 7.3 入力値を許可リストで検証する

`storeId`は、サーバー側で定義した有効な店舗識別子のみを受け付ける。型・形式・範囲を検証し、`|`等の予期しない構文を拒否する。

### 7.4 実行権限を最小限にする

アプリケーション実行ユーザーに管理者権限を与えず、不要なファイルの読み書き・コマンド実行・ネットワークアクセスを制限する。

### 7.5 検知・監視

在庫照会への異常な値、特殊文字・コマンド文字列を含むリクエスト、アプリケーションから起動された想定外のプロセス、突然のエラー増加を監視する。ログに機密情報を含めない。

## 8. 実務上の想定影響

類似した問題は、ping・DNS照会、ログ処理、バックアップ、画像・文書変換など、外部入力を使ってシステムコマンドを構築する機能にも起こり得る。

悪用された場合の影響は実行ユーザーの権限に依存するが、情報漏えい、ファイルの書き換え・削除、サービス妨害等に発展する可能性がある。

**本ラボで確認したのは`whoami`の実行結果の返却のみであり、管理者権限取得や任意ファイルの改ざんを実証したものではない。**
